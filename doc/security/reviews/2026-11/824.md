## 1. Is the stated cause the real one?

**Mechanism.** In Chromium, each web `MediaStreamTrack` that goes to a sender gets one WebRTC video track with its own source. That source adapts frames to the combined sink wants of every encoder it feeds, and the most restrictive `max_pixel_count` wins.

On main, the best line and both lower lines were three separate senders on the same track. When the best line's encoder asked for fewer pixels because of bandwidth (`degradationPreference: 'balanced'`, senders.ts:43), the shared source shrank its frames for all three lines. Each lower line then applied its fixed `scaleResolutionDownBy` on top of that.

A clone is a new web track on the same capture source, so it gets its own adapting source. This is the same reason simulcast layers inside one sender do not drag each other down.

**CI evidence.** I read run 43503313142, job `e2e-shard (1/4)` (id 132156049825). Its head was 74f978e9b: the fixture commit plus a diagnostic, without the client fix. The `[sharer]` lines at log lines 1762-1764 show:

| Moment | Best line (mid 2) | 640 line (mid 6) | Thumbnail line (mid 7) |
|---|---|---|---|
| tile | 1280x720, limit=none, inactive | inactive | 320x180, limit=none, changes=0 |
| stage | **640x360, limit=bandwidth** | inactive | **160x90**, limit=none, changes=0 |
| back to tile (45 s later) | inactive | inactive | **240x135**, limit=none, changes=0 |

- 160x90 is 640x360 / 4, and 240x135 is 960x540 / 4. The thumbnail followed the best line's adapted input exactly.
- The thumbnail's own encoder never reported a limitation or a resolution change.
- The assertion `toBe(180)` failed with `Received: 135` (camera-layers.spec.ts:133).

That is the pattern a shared adapting source produces. An encoder that limits itself would show `limit=bandwidth` or `cpu` and a non-zero change count.

**With the fix.** On 225f30a8f, job `e2e-shard (1/4)` (132189945127) passed camera-layers.spec.ts:74 on the first attempt in 57.9 s. The project has `retries: 1`, and no flaky result was reported. camera-visibility.spec.ts, which failed in the earlier run at its join step (line 72, unrelated to layers), also passed.

Verdict: real cause, and the fix targets it.

## 2. Clone lifecycle (camera light)

The clones live in `st.cameraLayerClones` (state.ts:70, :165). They are made in `layerClone` (cameraLayers.ts:53-61) and stopped in `dropLayerClone` (:64-67). `layerClone` reuses a held clone only when it copies the same capture and is still `live`. Otherwise it stops the old clone first.

| Path | What happens | Evidence |
|---|---|---|
| `stopCamera` (button, `toggleCamera`) | `releaseCameraLayers` takes every line off and stops every clone, then the capture stops | camera.ts:91, cameraLayers.ts:74-77 |
| Capture `onended` (device gone) | calls `stopCamera`, same as above | camera.ts:38 |
| Leaving the call, being taken over | `endCall` runs `cleanupPeerConnection` and then `stopCamera`. The senders are already null, but the clones array is not, so the clones are still stopped | session.ts:217, :220 |
| Call becomes unprotected | `onMediaUnprotected` runs `stopCamera` | useWebRTC.ts:48-51 |
| `restartCamera` / new device | `stopCamera` first, then `startCamera`. A leftover clone of the old capture would be replaced because `source` no longer matches | camera.ts:102-106, cameraLayers.ts:55-56 |
| Line no longer fed (no plan for it, or no track) | line taken off and its clone stopped | cameraLayerSync.ts:38-41 |
| `replaceTrack` on a line fails | the clone stays held but is on no sender. It is stopped by the next `stopCamera`, or reused by the next sync | cameraLayerSync.ts:19-20, cameraLayers.ts:37-43 |
| Reconnect / new connection | `cleanupPeerConnection` resets the senders but keeps the clones. The next `syncCameraLayers` puts the same clones on the new lines, and no new copy is made (test at :180) | peer.ts:31, :245 |
| Sync in flight while the camera stops | the check before `layerClone` runs synchronously against `st.localCameraStream`. `stopCamera` clears that stream in the same synchronous block as `releaseCameraLayers`, so no clone can be made after it. A clone already passed to a pending `replaceTrack` has already been stopped. A stopped track keeps nothing open | cameraLayerSync.ts:18-20, camera.ts:86-95 |
| Capture discarded after a late `getUserMedia` | no clone exists yet | camera.ts:72-75 |

`st.localCameraStream` is replaced only by `startCamera`, which requires it to be empty (camera.ts:29). So no path swaps the capture without going through `stopCamera`.

**No path leaks a clone beyond the camera's own lifetime.** Two paths keep a clone alive but unused while the camera runs: a failed `replaceTrack`, and a reconnect whose offer has no camera layer lines (note 2). In both cases the main capture is live anyway, so the camera light reflects the truth.

## 3. E2EE

- Media frames are sealed per sender. `bindTransceiver` (senders.ts:94-104) calls `mediaCall().protectSender` before it sets the line to `sendrecv`, and returns `null` when that fails.
- `protectSender` ends in `guard.arm`, which sets `sender.transform = new RTCRtpScriptTransform(...)` with the line's source and layer (guard.ts:193-212).
- `st.cameraLayerSenders[i]` is only ever set from that return value (senders.ts:155-158), and is reset to null with the connection (peer.ts:31).
- Clones are placed only through `feedLowerLayer` onto those senders (cameraLayerSync.ts:19-20). So a clone can only go onto a sender whose transform is already armed.
- `replaceTrack` swaps the track and leaves `sender.transform` and its port as they are. The transform options (source camera, layers 1 and 2) are the same as before.
- Between a reconnect and the rebind, the held clones are on no sender at all.

Conclusion: the lower-layer senders are protected exactly as before, and no path sends a clone before its sender is protected. No file under `web/src/lib/media/` changed.

## 4. Cost (reasoned, not measured)

- **Capture:** unchanged. A clone shares the capture source, so the camera is opened and read once.
- **Encoders:** unchanged. There was already one encoder per line, and inactive lines (`active: false`) encode nothing.
- **Per frame:** each clone adds one track and one WebRTC source on the frame path. The frame buffer is passed by reference, not copied. When a line's source adapts, it may scale the frame itself. Before, one shared source did that scaling for all lines. Now up to two extra downscales can run per frame, and only while those lower lines adapt. This is small next to encoding.
- **Memory:** a few objects per clone, no extra frame buffers in steady state.
- **Behaviour change:** the lower lines no longer shrink with the best one. Under a bandwidth limit, the 640x360 line can now be larger than an adapted best line. Its 500 kbit/s cap still bounds what it costs. Before the fix this inversion could not happen (note 4).
- **Not measured:** CPU, power and memory on a real device, with all three lines active and while adapting. CI does not measure them, and this review ran no browser.

## Notes (none blocking)

1. **Test gap:** no test checks that a line that is no longer fed stops its clone (cameraLayerSync.ts:40). Removing that line leaves all 10 tests green. The effect is bounded: the camera runs anyway, and `stopCamera` stops the clone later. A case with a capture that shrinks below a layer's plan, or with a camera too small after a restart, would pin it.
2. **Unused clones after a reconnect without layer lines.** `runSyncCameraLayers` returns early when no camera layer sender is bound (cameraLayerSync.ts:28). It also skips a null sender (:36). So after a reconnect to an offer with fewer or no camera layer lines, the old clones stay live and unused until the camera stops. This is not a camera-light leak, because the capture is live. Dropping the clones of unbound lines there would make the state match the lines.
3. **Style:** `LayerClone` is declared between two import blocks (state.ts:12-14). Lint accepts it. Moving it below the imports would read better.
4. **Behaviour change under congestion.** Each line now adapts on its own, so a bandwidth-limited best line can come out smaller than the 640x360 line. A viewer on the stage then receives less than one on the medium layer would. Simulcast avoids this by dropping top layers instead of shrinking them. The change is acceptable and capped by each line's `maxBitrate`, but no test or CI step watches it.
5. **The screen share has the same pattern.** `feedLayer` puts the screen track itself on every lower screen line (layers.ts:78). With `maintain-resolution` (the detail preset) the encoder does not ask for fewer pixels, so the effect should be limited to the motion presets. Worth a follow-up check with the same `sentVideo` diagnostic. It is out of scope here.
6. **Cost not measured** (section 4).
