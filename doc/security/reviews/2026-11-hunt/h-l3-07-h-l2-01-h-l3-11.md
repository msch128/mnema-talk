## 3. H-L3-11, commit 28d39a5f7: MERGE AFTER FIXES

### White-space set: identical to the server's, as far as messageText goes
httpx.CleanText (internal/httpx/request.go:99-110) does `strings.TrimSpace`, then refuses invalid UTF-8 and
NUL, then counts runes. Message content reaches it through core.ValidateContent for create
(service_gate.go:114), edit (message_mutations.go:64 and the handler) and scheduled messages
(internal/later/scheduled_handler.go:95, 149). Nothing else is stripped on the message path. Go's
TrimSpace set is ASCII `\t \n \v \f \r space`, U+0085, U+00A0 and unicode.IsSpace above Latin-1 (U+1680,
U+2000-U+200A, U+2028, U+2029, U+202F, U+205F, U+3000). `SERVER_SPACE` in textLength.ts lists exactly
these. Probe over all BMP code points: messageText's edge trim differs from JavaScript's trim() on exactly
U+0000 (stripped, by design), U+0085 and U+FEFF. So the helper itself matches the server.

### BLOCKER 1: the store still trims with JavaScript's trim(), so the wire is not what messageText returns
`messageText()` is applied in the components, but the store applies `.trim()` again before the request:
- web/src/stores/chat/messagePost.ts:73 `content: withEmojiTokens(send.content.trim())` (every text POST,
  the outbox's retries included),
- web/src/stores/chat/messageActions.ts:23 (`!content.trim()` guard in sendMessage), :72 and :75
  (editMessage guard and PUT body).

Consequences, each traced through the real code:
- (a) The defect of the finding is still there for a variant. Draft `"﻿\u0085﻿"`: messageText
  keeps it (U+FEFF is not server white space), so the send button is enabled; the store's trim() removes
  the two U+FEFF and sends `"\u0085"`; the server's TrimSpace makes that empty and answers 400 "content is
  required". The same goes for `"﻿ \u0085 ﻿"` and for editing a message to such a text.
  Evidence: a throwaway vitest (not committed) that mocks `api` and calls `postText` with
  `messageText(draft)` saw the JSON content `"\u0085"` for that draft; a Go `strings.TrimSpace` of it is
  empty.
- (b) The commit message's claim "it keeps U+FEFF ... exactly as the server does" is false on the wire:
  the request still loses U+FEFF at the edges.
- (c) A draft of only U+FEFF (or U+FEFF with white space): the send button is now enabled (before: disabled);
  `sendMessage` returns null because `content.trim()` is empty; ChatArea.handleSend does not look at the
  result and clears the composer. The member's draft vanishes, nothing is sent, no hint. Message edit of
  the same text closes the editor without saving or asking to delete (saveOrDelete now goes to saveEdit,
  editMessage returns null). An outbox entry edited to `"﻿"` used to be cancelled; now it is kept and
  sent as an empty content, which the server refuses with 400.
- (d) The parity test does not see any of this: `composerSends` models the components only, not the store.
  Of the 552 regenerated vectors, 70 differ from what the store actually sends, and for 20 of them the wire
  content is empty. Their `runes` are counted on a string that is never sent (the wire is shorter, so the
  "within the limit" property still holds, on the safe side).

Fix (suggested, smallest): make messageText also remove U+FEFF at the edges (trim with the union of Go's
set and trim()'s set). Then the store's trim() is a no-op, the server's TrimSpace is a no-op, the counter
equals what is stored, and the U+FEFF behaviour of the web client does not change. Alternatively remove the
store's `.trim()` calls and decide deliberately that the web client may now send U+FEFF-led messages (the
server has always stored them for API clients and bots; invisible messages are already possible with
U+200B). Either way, model the wire in the test: let `composerSends` end with what `postText` puts in the
body (or test `postText` with a mocked `api`, as above), and add `"﻿\u0085﻿"` and `"﻿"` to
the unit check.

### BLOCKER 2: messageText is quadratic in a run of white space, on the composer's render path
`edgeSpace = /^[S]+|[S]+$/g` makes the engine try `[S]+$` at every position of an inner white-space run and
backtrack, so the cost is the square of the longest inner run. Measured in Node 24 (one call; trim() takes
under 0.01 ms for all):

| inner run of spaces or newlines | messageText |
|---|---|
| 4 000 | 9 ms |
| 20 000 | 190 ms |
| 50 000 | 1.1 s |
| 100 000 | 4.8 s |

It runs on every render of the composer (`:disabled` in ChatComposer.vue and ThreadComposer.vue, the
`canScheduleLater` and "send later" computeds) and in `lengthState` from 3 600 UTF-16 units on, so a pasted
text with a long blank stretch freezes the tab on each keystroke, and again when the draft is restored.
Only the author's own tab is affected, but it is a new cost on a hot path that trim() did not have. Fix:
trim with two index loops (or two anchored, non-global regexes applied to a string already known to end in
a non-space, e.g. find the last non-space index first). Add a timing-free unit check, for example a 200 000
character inner run that must finish, so a regression shows up as a test timeout.

### SHOULD-FIX
1. web/src/chat/components/ScheduledItem.vue:38 and :43 still use trim(). The schedule creation path
   (ChatComposer "send later") now uses messageText, but editing a scheduled message to a U+0085-only text
   is still sent and refused with 400 by the same ValidateContent (scheduled_handler.go:149), and a NUL in
   it is still refused rather than stripped. Same class as the finding, one line each; the commit
   message names it but leaves it. Use messageText there too.

### NOTE
1. Outbox entries stored before the update are not re-cleaned on load (outboxStorage.ts:46-54 reads
   `content` as stored, clamps it only). An entry with NUL queued by the old client is retried as is and
   refused once with 400; editing it (saveEdit applies messageText) repairs it. The dedupe key is the nonce,
   which the change does not touch; the edit-retry path (`saveEdit`, possiblyDelivered and sending guards)
   is unchanged apart from the cleaning. Acceptable.
2. Counter versus server: for every text whose wire equals messageText (all except U+FEFF edges) the
   counter's rune count equals the server's `runes` in the vector file. With U+FEFF edges the counter counts
   one or two more than the server stores, so a 4 001-character draft with a U+FEFF edge is blocked
   although the server would take it. Safe side; goes away with BLOCKER 1's first fix.
3. NUL is now stripped, not refused: "a\u0000b" is sent as "ab" where the server used to refuse it. That is
   a deliberate behaviour change, documented in the commit message, and nothing renders NUL. Fine.
4. Remaining `.trim()` uses that do not decide what is sent (typing indicator ChatComposer.vue:105, Escape
   handling useComposerKeys.ts:53, drafts.ts:200 keep-or-drop of a draft, previews) are harmless; drafts.ts
   keeps a U+0085-only draft, which is only a stored draft.
5. contentParity.test.ts unit check line has a stray space before `)`; ESLint does not flag it.

### Vector file and the Go side
Only `internal/chat/core/testdata/content_vectors.json` changed outside web/. Before: 570 vectors, 88
refused. After: 552 vectors, none refused. `TestContentVectorsMatchTheServer` still reads the file
(content_parity_test.go:24-46) and passes, so the file holds the server's real verdicts for these strings.
Reverting messageText to `draft.trim()` makes "the vector file holds what the composer sends" and the new
unit check fail; "the server accepts everything the composer sends" stays green on revert because it reads
the static file, which is fine since the equality test guards the file.
