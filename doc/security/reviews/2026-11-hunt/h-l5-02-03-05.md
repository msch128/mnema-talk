### Reviewer's own property test (re-apply logic)

A random model (reviewer file, not committed): a server set of saved ids, this session's PUT/DELETE
answered late and in FIFO order, another session's saves and removals with their `saved_updated` events,
message deletes (roots with saved replies), disconnects that lose every event not yet delivered, a
reconnect that calls `refresh()`, and GET pages that the server reads at a random moment and that arrive
in any order. Oracle at quiet: the client's items equal the server's set, and `isSaved` equals it.
To keep the oracle free of races the store cannot know about (two writers on one id), local and remote
operations use disjoint ids and a message is deleted only while no own write on it is in flight.

- 2,000 seeds x 60 steps, roots only, and 2,000 seeds with thread replies: **items equal the server in
  every run.** The re-apply of changes made while a page was in flight (saved.ts:25-53) holds; I found no
  duplicate and no lost row from late answers.
- **`isSaved` wrong in 74 of 2,000 (roots) and 122 of 2,000 (with replies) runs**, always one extra mark:
  see SHOULD-FIX A1.

### Findings

**SHOULD-FIX A1: a reconnect clears stale saved marks only when its own page is the newest.**
saved.ts:100: `if (await load()) known.value = new Set(...)`. When another load starts while the
reconnect's page is in flight (an `onUpdated({saved: true})` from another session, saved.ts:115), the
reconnect's page is discarded (savedList.ts:25, `mine !== seq`), `refresh` gets false and `known` is never
rebuilt; the newer page only adds to `known` (savedList.ts:29 via `onEntries`). A message removed on the
phone while the socket was down then stays marked as saved in the chat although it is gone from the list.
Deterministic case (reviewer file): load [1]; socket down, 1 removed elsewhere; open -> refresh GET in
flight; `saved_updated` for 2 -> second GET; the refresh answer [] arrives, then [2]. Items [2] (right),
`isSaved(1)` true (wrong). That is part of what H-L5-02 claims ("one removed there still shows").
Fix direction: let the next applied replacing page rebuild `known` when a refresh asked for it (a flag set
by `refresh`, consumed by whichever newest page lands), rather than only the refresh's own answer.

**SHOULD-FIX A2: every reconnect cuts the open saved list back to the first page and drops the older
pages' marks.** `refresh` replaces `items` with the newest page (savedList.ts:26) and then sets `known` to
that page only (saved.ts:100). A member who scrolled the Saved tab to page 3 sees it collapse to 50 entries
on every socket open (a lid, a network change, every deploy); messages saved on page 2+ lose their saved
mark until that page is loaded again. Measured (reviewer file): load page 1 [1] (has_more), loadMore [2],
refresh -> items length 1, `isSaved(2)` false; on 82e51418f nothing happens on a reconnect. The list
collapse already happened before on `saved_updated` with saved=true (saved.ts:115 reloads the first page),
but now it happens on every open, and the mark loss is new. The comment on the store says not knowing is
harmless (saving again keeps the note), so this is not a data problem; it is a visible regression in the
open panel. Fix direction: on refresh keep `known` for ids older than the page's last entry, or reload as
many entries as were shown (`limit` up to the shown count, capped), or skip the list rebuild while the
panel is scrolled past page 1 and only fix the marks.

NOTE A3: newestOf narrows the due notice. later.ts:63-71 keeps only the newest request's answer. When two
`reminder_update` events arrive back to back (two reminders due in one sweep tick), the first event's answer
is dropped and `noticeReminderDue` (later.ts:139) reads the list before the second answer lands. If the first
reminder is not in the list yet (made in another session within the same window), the notice is the generic
"reminder due" without the Open action. Reviewer case: fails on 652ab1931, passes on 82e51418f. Narrow
(needs both events within one request round trip and a reminder unknown here); a real regression though.
Fix direction: let `onReminderEvent` await the newest load (keep the promise of the newest request and await
it) before it looks the reminder up.

NOTE A4: deletions that send no `message_delete` still leave saved entries until a reconnect or reload:
channel deletion (internal/chat/channels/channels.go:163, client gets `channels_changed`), a DM conversation
deleted with its last member (internal/chat/dm/dm_members.go:121), deleting a webhook's bot user with its

`channels_changed`).

until a reconnect or reload. Unchanged by this branch, not in the findings.

NOTE A6: `onMessageDeleted` calls `drop` for every deleted message, saved or not: each delete assigns a new

### Measurements (reviewer probe, real Postgres, not committed)

The lookup was slowed by replacing `thread_follows` with a view whose WHERE runs `pg_sleep` once per SELECT
(INSERTs into the view, as followOnReply does, do not evaluate it). One reply by a peer and, 20 ms later, one
plain message in the same channel; times from the reply's start; an observer socket (not a follower).

| Lookup | Fix: reply POST / reply frame | Fix: plain message frame | Base 82e51418f: reply POST / frame |
|---|---|---|---|
| no delay | 8-11 ms / 11 ms | 26 ms | 5-10 ms / 5-10 ms |
| 50 ms | 60 ms / 60 ms | 35 ms | 5-11 ms / 5-11 ms |
| 2 s | 2.01 s / 2.01 s | 31 ms | 5-9 ms / 5-9 ms |
| 6 s (beyond the 5 s timeout) | 5.007 s / 5.007 s, "context deadline exceeded" logged | 30 ms | (not run) |
| query error (division by zero) | 7 ms / 7 ms, error logged | 32 ms | (not run) |

So:

- The tap blocks only its own publisher: the reply's HTTP request and that reply's delivery to everyone wait
  for the lookup. Other publishes of the hub do not wait (the plain message arrives at ~30 ms while the reply
  is held 2 s): `BroadcastChannel` and `Broadcast` call the tap before taking `h.mu` (perms.go:70-72,
  broadcast.go:46-50).
- The lookup is bounded: a context with `followSyncTimeout` (5 s) on the server's context, covering the
  permission snapshot and the query. After a timeout or a query error the reply is still delivered (fails
  open for the delivery, closed for the follow update). That is right.
- Goroutines: the four permanent workers are gone; per reply no goroutine before or after (the old tap only
  enqueued). Allocation per reply: the same `core.Message` copy as before, no channel send. The probe's
  goroutine counts (45 -> 48 at the delayed runs) are the test's own reader and HTTP keep-alive goroutines.
- What the removed queue did: it bounded concurrent lookups to 4 ("so a burst of replies cannot take the pool's
  connections from the request handlers", added in #469 after the very first version ran one goroutine per
  reply) and dropped updates when 256 were queued. Now the lookup runs in the publisher's goroutine after its
  transaction committed, so concurrency equals publishing concurrency and each publisher holds at most one
  connection at a time; no back-pressure is lost that the request path did not already have. The queue's
  goroutines used `safego.Crash`, so a panic in the lookup ended the process; now it unwinds into the
  publisher (HTTP recovery, or the publisher's own safego policy). Not worse.
- Serial publishers: the scheduled-message sweep sends due messages one by one (internal/later/scheduled_send.go:62-72,
  `sendTimeout` per message); each scheduled reply now waits for its lookup too. Milliseconds normally, up to
  5 s each with a stalled database.

### Findings

**SHOULD-FIX B1: the hub's tap contract now says the opposite of what the follow tap does.**
internal/ws/hub.go:33-42: Tap "must not block and must not call back into the hub: it runs next to the hub's
lock, and a call that takes that lock again can wait forever behind a writer"; DMTap "must not block". The
follow tap now blocks for up to 5 s and calls back into the hub (`SendToUsers` takes `h.mu.RLock`,
broadcast.go:67). It is safe today only because `message_create` is never published through
`publishScoped` (event_scope.go:55-57), which calls the taps with `h.mu` read-held: a reply published there
would take the read lock twice, and a writer waiting in between (register/unregister) deadlocks the hub
(sync.RWMutex blocks new readers behind a waiting writer). Nothing guards this. (The bot gateway's tap,
internal/gateway/observe.go:70-90, already blocks up to its 3 s permission load, so "must not block" was
loose before; the call back into the hub is new.) internal/ws/hub.go is the
package's bug magnet. Fix: update the Tap and DMTap docs to the real rule (called without `h.mu` on the
`BroadcastChannel`/`Broadcast` paths, may block for a bounded time, may publish), and either move the tap
call in `publishScoped` out of the lock or add a test that fails if a tap runs with `h.mu` held.

**SHOULD-FIX B2: a held reply can now be overtaken by events of the same message.**
The taps are chained in registration order (router_build.go:248-256): the bot gateway (newBots,
router_build.go:243) is added before the follow tap (server.go:179-180), Web Push after it. The gateway
queues the reply to the bots' sessions (internal/gateway/observe.go:70-100) before the follow tap starts its
lookup, so a bot sees the reply up to the lookup time before any web client does. (Outgoing webhooks get
message events from the transactional outbox, internal/webhook/dispatch.go:274-281, independent of the tap,
so they could already run ahead of the hub; the held create widens that window too.) A moderation bot that deletes
or edits it in that window publishes `message_delete`/`message_update` (no lookup on those) before the
`message_create` reaches the clients, and the web client then adds a message that is already gone (a ghost
until reload). The window was microseconds before; it is now the lookup (ms normally, up to 5 s with a slow
database). Not reproduced (needs a bot gateway client in the probe). Fix direction: register
`tapThreadFollows` before `newBots`, so the blocking step comes before the gateway hands the reply out;
or note the ordering assumption in doc/architecture.md.

NOTE B3: the client-side guard. storeFollow.known.test.ts now feeds the frames in the server's new order;
the client is unchanged, so the test passes on the 3.0.9 client too: it documents the protocol and guards
nothing. The checked-in traces are recordings, so the trace smoke would also stay green if the server
change were reverted. The only regression guard is the Go integration test, which is deterministic with the
fix (one goroutine) and failed 3 of 3 without it. That is acceptable: the property is a server ordering
property and it has a server test. What stays open on the client: the resync's `fetchFollowedThreads`
assigns its answer (threadFollow.ts:27), so an answer read before a reply's commit and arriving after its
`thread_follow_updated` removes the thread again and the first reply after a reconnect is decided without it
(the followed-threads half of H-L5-04, already in storeTrace.known.ts as "drop+late followed"); and a
lookup that times out or fails sends no update (logged, as the commit says).

NOTE B4: an explicit unfollow racing a reply's lookup (the lookup reads following=true, the unfollow commits
and sends following=false, then the tap sends following=true) leaves the open client following until the
next list load. It was so with the worker queue too (wider window then).
