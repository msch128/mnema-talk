# H-L3-05

## 1. Does it remove the cause

Cause (finding, refuter): `messageMentionsMeDirectly` matched `@username` in the raw text and never looked at
`msg.mentions`, the list the server resolved under the sender's mention policy. The fix adds one guard
(`web/src/stores/chat/notifications.ts:42`): when the payload carries a `mentions` array without me, the
message is not addressed to me. A reply to me still counts first. Being on the list is necessary, not
sufficient; the old text and role checks then separate a name or role mention from `@all`/`@here`.

This is the right place: the same function feeds every variant the refuter listed: the muted badge
(`events.ts:146`), the page's OS notification (`notifications.ts:76`, `shouldNotify` lets `mute` through only on
isDirectMention), the sound (`messageSound.ts:36`), the thread-follow filter (`threadAllows`) and
suppress_everyone (`messageMentionsMe` delegates to it). Reasoning against the server:

- The wire list is authoritative on every live path. Every `message_create` broadcast is a message loaded back
  from the database (`GetMessage` in `post.go` publishCreated/PublishMessage, `webhook/execute.go:227`,
  `bot/interactions_respond.go:191`, `poll/service.go:77`, outbox), and `loadMentions` fills `Mentions` from
  `message_mentions` (`messages.go:135-148`, initialised to `[]`). The poll's empty-list fallback is only the
  author's own HTTP response, not broadcast.
- Server rule for a mute (`readstate.go:47-49`, `push/recipients.go:177`): addressed = a reply to me, or a
  `message_mentions` row of kind name (0) or role (2). The server stores kind 0 only for listed users whose name
  is in the text (`queryMentioned` CASE) and kind 2 for listed role members (`addRoleMentions`). So "listed AND
  (text names me OR a mentioned role is mine)" is the server rule, with the exception in N1.
- Role mention over the recipient cap: `capRecipients` drops users but keeps `Roles`, so `mention_roles` still
  lists my role while I am not in `mentions`. Before the fix the client counted it, the server did not; after
  the fix both do not. Same for the 100-name cap (`maxMentionNames`) and for `CanView`.
- Older server without the list: `Array.isArray` is false, the text rule stays (probe P3).

# H-L3-06

## 1. Does it remove the cause

Cause: raw Markdown cut to 200 characters before stripping. The fix adds `mdplain.Snippet` (Go,
`internal/mdplain/snippet.go`) and `markdownSnippet` (web, `web/src/shared/lib/markdown/snippet.ts`): a message
of at most 200 code points is returned as it is; a longer one is reduced to plain text (spoilers as a
private-use mark), white space collapsed, cut to 199 plus "…", then escaped back into Markdown with each
spoiler written as `||…||`. All sites named by the finding and the refuter use it: reply quotes
(`messages_scan.go:35`; `MessageSelect` reads `rm.content`), the client's edit path (`replies.ts`
markPreviewEdited), search roots (`search_roots.go:53`), reminders (`later/visibility.go:55`, which feeds the
list, the in-app notice and the reminder push), plus the conversation list (`dm.go:202` and the client's
`lastMessageOf`), which the finding missed. Saved items, forwards, message pushes and OS notifications
already stripped the whole message (refuter's table), confirmed.

Against its own parser on each side the fix holds:
- Go deep sweep, run myself: `PLAIN_SWEEP=1 go test -run TestSnippetNeverShows ./internal/mdplain` ->
  "100000 messages, 13519 cut, 0 leaks". Round-trip test (20,000 strings) passes.
- Web deep sweep, run myself: `PLAIN_SWEEP=1 PLAIN_SWEEP_N=100000 npx vitest run plainSpoiler.test.ts
  snippet.test.ts replies.test.ts src/dm`: 8 files, 126 tests passed (the sweep asserts zero leaks; the
  reporter does not print its console line for a passing test).
- My own web generator (a richer alphabet: `+ `, `2) `, `-#`, entities, `<@id>`, `<:emoji:id>`, `<t:…>`,
  autolinks, ZWJ families, flags, combining marks, surrogate pairs, fences, escapes; 100,000 messages, 85,450
  cut): 0 snippets whose `previewText` shows a hidden canary, 0 whose `renderMarkdown` contains one, and
  `previewText(snippet)` equals the expected cut plain text in every case.

But the server's snippet is built by the Go parser, and every client now shows what the Go parser decided.
That is B2.

### B2 (BLOCKER): the server's parser now decides what web clients show, and it disagrees with the web renderer

Before the fix, the web client stripped the (raw) reply quote with the web parser, the same parser that renders
and hides the spoiler. After the fix, for a message over 200 characters, the server reduces it to plain text with
`mdplain.Plain` and the client only reads that back. The commit's premise ("any reader that strips it with this
flavour ... gets exactly the cut plain text") holds only if `mdplain.Plain` hides exactly what the web
renderer hides. It does not. Each side's sweep checks the side against itself, so neither can see this.

Cross-check (my generator, 100,000 messages; oracle: the web `previewText` of the whole message, which the
commit's own test ties to the renderer):
- the Go snippet shows text the web renderer hides in 940 messages;
- the web reply preview leaked before the fix in 3,267 messages, after the fix in 940: 3,061 fixed, but
  **734 messages that were hidden before now leak**;
- `mdplain.Plain` of the whole message (the message push, pre-existing) disagrees in 978.
- Go and web snippets differ for 2,199 of the 100,000 (so a reply quote also changes text when the client
  rebuilds it after an edit).

One class, minimised: a precedence difference between emphasis and code spans when the emphasis spans a
paragraph break. The web parser lets the code span win, `mdplain` the emphasis, so the `||` inside the code
span pair up differently and text between spoiler markers comes out visible. Minimal input and its outputs on
both sides are in a separate, non-public note for the coordinator (this fix is not released).
Not all 734 are classified; other classes may exist.

Concrete failing scenario: a member writes a long message (over 200 characters) of that shape with a spoiler
inside the first 200 characters. Before the fix every reader's reply quote hides the spoiler; after it, every
web and desktop client shows its text in every reply quote, the conversation list, the search root and the
reminder list. Same S3 effect as the finding, new trigger.

Fix direction: make `mdplain.Plain` agree with the web parser (here: code spans before emphasis), and add a
cross-implementation check, for example a generated corpus checked into testdata with the web renderer's hidden
set (or the web `previewText`) recorded, checked by a Go test against `Plain` and `Snippet`. The shared
`snippet.json` has 14 hand-written vectors and does not catch it. This also fixes the pre-existing push leak,
which deserves its own finding (see N6).

## 3. Does it introduce a defect (other than B2)

### API (lead's question)

doc/api-stability.md: field types are unchanged, so the change is not breaking by its rules; it is a change of
what a documented string contains, which the commit states in `doc/upgrade.md` and the OpenAPI descriptions
(`make openapi-check` passes; `npm run contracts:check` passes; event golden tests pass).

- Old web clients and the desktop client (which runs a web bundle): I copied the strip code of v1.0.0 and
  v3.0.0 (`web/src/lib/markdown*`, `replies.ts`) and ran their `previewText` on 85,450 new snippets: identical
  to the new client's output in every case. No stray backslashes: every character the escaper prefixes is a
  symbol both old parsers already treat as escapable (any non-alphanumeric, non-space character), and `||…||`
  reads as a spoiler there.
- Bots, outgoing webhooks, third-party clients that render these fields as Markdown: see S3.

### S2 (SHOULD-FIX): worst-case cost on read paths is about 80 times the measured figure

Benchmark confirmed: `BenchmarkSnippetOfALongMessage` 27.5-28.5 µs/op, 36.7 KB, 261 allocs (M-series Mac,
3 runs). But `mdplain.Plain` is quadratic on some inputs, and the four queries now run it on up to 4,000
characters per row, per reader, per load (before: 200). Measured `Snippet` on 4,000-character inputs:
`[a](` repeated 1.6 ms, `[` repeated 0.86 ms, mixed openers 0.1 ms. `Plain` on `[a](` repeated:
500 chars 44 µs, 1,000 176 µs, 2,000 707 µs, 4,000 2,260 µs (quadratic). Anyone who can post can make
a message page that quotes 50 such messages cost about 100 ms of server CPU for every reader who opens it, and
the same on the DM list and search roots. Before the fix this cost was paid once per message by the push only.
Not a blocker (bounded by MaxMessageLen and page size), but the commit's "1.3 ms per page" is the typical case,
not the bound. Options: make the link-opener scan in `mdplain` linear (it already memoises misses for other
openers), or build the snippet once at write time, or at least memoise per quoted message within a query.

### S3 (SHOULD-FIX): document that a snippet can exceed 200 characters and is no longer Markdown from the message

- The escaped snippet is longer than its plain text: up to about 5 characters per plain character (each
  spoiler mark becomes `||…||`, each symbol gets a backslash). Measured: 996 characters for a long run of `|`,
  399 for runs of `[`, `*`, `<`. The old OpenAPI text said "at most 200 characters" for `last_message.text`,
  the search root `snippet` and the reminder `snippet`. api-stability.md counts a larger maximum as not
  breaking, but `doc/upgrade.md` should say it, and the new descriptions ("the first 200 characters of its
  plain text as Markdown") can be read as a 200 bound.
- A reader that renders the snippet as Markdown (a bot, a third-party client; not ours: every web site strips
  it) now sees text the original showed as code: a URL that was inside a code span becomes a live autolink
  (`` `https://x.example` `` gives a bare link; the link text is the URL itself, so no disguise), and an
  `@everyone` inside code becomes a mention pill (display only: the server's notification is decided on the
  message, and its parser already treats code-span mentions as real). No hidden text, no new notification,
  and custom emoji, `<@id>` and `<t:…>` tokens are neutralised by the escaped `<`. `doc/upgrade.md` names bots;
  it should also name outgoing webhooks (`message_create` deliveries carry `reply_to.content`).

### Escaping, edges (lead's questions)

- Can a crafted message make the snippet contain hidden text, a link or a notifying pill: against the web
  parser, no (B2 aside, which comes from the Go parser, not the escaper); links and pills only as in S3.
  A spoiler in the snippet holds only "…": clicking it reveals "…".
- 200 and 201 characters: 200 code points is returned raw (spoiler intact, hidden by the reader); 201 goes
  through plain, ends `… ||…||` and reads "Spoiler". Checked in Go.
- Surrogate pairs, ZWJ sequences, flags, combining marks at the cut: both `textcut.Runes` and `clampChars`
  back up to a character boundary; checked with emoji, a ZWJ family, a flag pair and `e` + U+0301 at the cut:
  no broken character.
- `&#57344;` (an entity for the private-use mark) stays literal in both parsers; a U+E000 in the message is
  dropped before marking (test exists).
- A long message whose plain text is empty (for example a long `[](url)`) gives an empty snippet; with
  `omitempty` the reply quote then has no `content`. Harmless.

## Can Go now be sure and wrong?

I recorded the client's `safeHref` answer for 60,216 targets and compared them with the Go port wherever it
says it is sure. The targets: 71 hand-written authorities, each under `http://`, `https://` and `HTTPS://`,
plus 20,000 random authorities built from `% %2E %2F %40 %3A %25 %00 %41 %C3%A9 %E2%80%8B %7F %5C %5B %5D @ :
[ ] \ 0x`, U+200B, U+00AD, U+0085 and letters, digits and dots.

The hand-written cases:
- `%2540` and `%252E` (double encoding);
- `%00`;
- encoded dots, including `%2E%2E`, a trailing `%2E` and lower-case `%2e`;
- encoded `/`, `\`, `@`, `:`, `#`, `?`, `%`, `[`, `]` and `|`;
- encoded port separators, and ports with `%`, `+`, `-`, a space and leading zeros;
- encoded IPv4 shorthand: `%31%32%37.1`, `0x%37f.1`, `%30X7F.1`, `127.%31`, 4294967295 and 4294967296
  encoded, and `a.%31`;
- encoded DEL, TAB and LF;
- NBSP, soft hyphen, BOM, ZWSP and emoji percent-encoded;
- `xn%2D%2D`;
- backslash before `@`;
- user info, written and encoded.

Result: **0 answers where Go is sure and wrong**, and 3,672 left to the browser. The decoding mirrors the URL
parser:
- an encoded `@`, `/`, `:`, `%`, `\` or `[` decodes to a forbidden domain code point, so the host is refused,
  as the browser refuses it;
- `%2540` decodes once to `%40` and is refused for its `%`;
- `%00` is refused by the Cc rule;
- encoded dots and digits feed the same label and IPv4 logic as written ones;
- the port is split on the raw `:` before decoding, as in the URL parser.

## Cc and Cf, Go against JavaScript

`linkAuthority.ts` tests `/[\p{Cc}\p{Cf}]/u`. Go's `hidden` tests `unicode.Cc` and `unicode.Cf`. I compared
the two over every code point:
- Go 1.27.4 has Unicode 17.0.0, Node 24.12 has Unicode 16.0 (ICU 77.1).
- Both sets have 235 code points and are identical, with no code point in only one of them.

A user's browser may run an older Unicode version, where a few code points that are Cf now (for example the
Egyptian format controls U+13439 to U+1343F, added in 15.0) are unassigned. There Go refuses the link as
"hidden" while the old browser's regex does not match. But an unassigned code point is disallowed by that
browser's IDNA, so it refuses the host too, and both readings agree that it is no link. In a path or query the
rule does not apply on either side. No disagreement follows (N11).

## The drift guard

I mutated `linkAuthority.ts` two ways:
1. dropped the `authority.includes('@')` test;
2. narrowed `HIDDEN` to `\p{Cc}`.

Each time `hrefParity.test.ts` failed ("the recorded answers are the client's"). After `HREF_UPDATE=1`,
Go's `TestSafeHrefAgreesWithTheClient` failed: 3 or more mismatches after mutation 1, such as
`safeHref("http://@h.x/") = false, the client says true`, and 8 after mutation 2. Restored afterwards. So a
change to the client rule cannot pass both sides unnoticed.
