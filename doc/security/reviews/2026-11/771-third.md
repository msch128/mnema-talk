  The filter maps io.ErrUnexpectedEOF to io.EOF, but that is also the error the SOURCE reports for an upload that stops early (multipart.Part.Read without closing boundary). Input: form body "--boundary\r\nContent-Disposition: form-data; name=\"file\"; filename=\"a.bin\"\r\nContent-Type: image/png\r\n\r\n" + first 2/3 of a PNG, no closing boundary, via Handler.readUpload with a MemoryStore: PNG and JPEG give err=nil, object stored (109 of 164 bytes, 968 of 1452); the same form with GIF or text/plain gives 400 "invalid multipart form" and no object, which is what main does for every type (the next NextPart returns "multipart: NextPart: EOF", which readParts takes for the end of the form, so only Store.Upload's read error rejected it before). At imgstrip level: a reader that ends with io.ErrUnexpectedEOF returns err=nil for JPEG, PNG, WebP buffered and WebP streamed; any other error is passed on correctly in all paths. Limit of the damage: a connection that really breaks (HTTP/1.1 with Content-Length, client closes early) is still rejected with 400 and nothing stored for all types (tested over a real TCP connection); webhook uploads use the same storePart. Fix: keep the source's own error apart from ReadFull's, e.g. wrap src in a small reader that records any error other than io.EOF and let take/jpegData/webpRead turn ErrUnexpectedEOF into EOF only when that record is empty; add the PNG/JPEG/WebP cases to TestStreamFormMapsTransportAndFramingFailures.

  F2 note - webp.go:27 and 148-149, webp_stream.go:53. Chunks inside ANMF frames are not looked at in either path. Input: VP8X(0x0E) + ANIM + ANMF{frame header, VP8L, "GPSx", "EXIF", "XMP " each with a marker} + ANMF + top-level EXIF(3) + "XMP ": top-level metadata goes (orientation 3 kept, flag right, idempotent), all three markers inside the frame survive, buffered and streamed. SECURITY.md says so ("the frames of an animated WebP with any chunk inside them"), so the docs are truthful; the spec allows unknown chunks there and decoders skip them, no real writer puts metadata there. Possible fix: walk the ANMF payload after its 16 header bytes and overwrite non VP8/VP8L/ALPH sub-chunks with zeroed JUNK in both paths (keeps all lengths). Same class, also covered by "the kept parts are not examined": ANIM with bytes after its 6, a second VP8L or VP8 chunk holding text: the marker survives.

  F3 note - jpeg.go:55-57 and 125-126. The JPEG allow-list covers APPn and COM only. A segment under DNL (FFDC), FFDE, FFDF, JPGn (FFF0-FFFD), reserved FF02-FFBF or FFC8 with a marker string placed after SOI survives whole. Go's decoder rejects these files and libjpeg aborts on all but DNL, cameras do not write them, and the docs say "application segment", so this is truthful; mention it under "what it does not do" or drop segments that are not SOF/DHT/DQT/DRI/SOS/DAC/DNL/EXP/DHP.

  F4 note - webp.go:74. Every WebP above 64 KiB allocates limit+1 = 5 MiB whatever its size (measured: 100 KiB file 5,324,816 bytes, 60 KiB file 73,744 bytes). Correct against N1, but N parallel WebP uploads hold N x 5 MiB.

  F5 note - imgstrip.go:184-190. Only the first EXIF record counts, also when it is empty or unreadable: PNG with eXIf(0 bytes) then eXIf(orientation 6) ends without orientation. Same rule in JPEG and WebP. Fine as a rule; not in the docs.

  F6 note - png.go:50. An unknown CRITICAL chunk (tried XMPD, IDAX, ABCD, JDAT, also IDAt/idat/iend) is dropped like any other and the result is the plain picture. A strict decoder would have refused the source and now shows it; Go's decoder ignored it before as well. I think this is right for a privacy filter (nothing survives, nothing breaks) and matches "any chunk under an unknown name".
