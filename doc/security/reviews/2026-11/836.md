## 1. Clone lifecycle (screen)

The clones live in `st.screenLayerClones` (state.ts:67, :167). `layerClone` (layerClones.ts:14-22) makes them and `dropLayerClone` (:25-28) stops them. `layerClone` reuses a clone only while it copies the same capture and is `live`. Otherwise it stops the old clone first.

| Path | What happens | Evidence |
|---|---|---|
| `stopScreenShare` (button, menu, logout, gaming action) | `stopScreenLayerClones` runs synchronously, before the capture tracks are stopped. `syncLayers` later takes the lines off | screen.ts:239, :245, :254; layers.ts:153-156 |
| Capture `onended` (the browser's own "Stop sharing") | calls `stopScreenShare` while the stream is current | screen.ts:35 |
| Leaving the call or being taken over | `endCall` runs `cleanupPeerConnection` (which keeps the clones) and then `stopScreenShare`, which stops them | session.ts:217, :219 |
| Call becomes unprotected | `onMediaUnprotected` runs `stopScreenShare` | useWebRTC.ts:48-49 |
| Source switched (`replaceScreenShare`) | old clones are stopped synchronously, right before the new stream is set, with no await in between. The new clones come from the next sync | screen.ts:220-223 |
| `retuneForCapture` (the capture changed size or rate) | all clones are stopped synchronously. The queued sync makes new ones | layers.ts:166-170 |
| Line no longer fed (no plan for it) | `dropTrack` stops its clone and takes the line off | layers.ts:56-59, :122-124 |
| No track or no best sender | `releaseLayers` drops every line's clone, then all clones again | layers.ts:62-71 |
| `replaceTrack` fails | the clone stays held but is on no sender. The next sync reuses it, and any stop path stops it. The capture is live then anyway | layers.ts:91 |
| Reconnect to an offer with fewer or no layer lines | `runSyncLayers` first drops the clones of every slot without a sender (`dropMissingSenderClones`), before its early return. `finishOfferNegotiation` now runs the sync when a share was bound or clones exist | layers.ts:135-136, peer.ts:241-243 |

**Race with the async `qualityChain`.** `feedLayer` checks the current capture (layers.ts:89) and makes the clone (:90) with no await in between. Every path that ends or swaps the capture does its clone stop and its `localScreenStream` change in one synchronous block:

- `stopScreenShare`: screen.ts:239 and :246.
- `replaceScreenShare`: :220-221.
- `endCall`: through `stopScreenShare`.

So an in-flight sync either made its clone before the stop, and the stop catches it, or it sees the new or empty stream and returns false. A clone made before the stop can still reach a sender through its pending `replaceTrack`, but by then it has already ended. A stopped track keeps no capture open. **No clone can be created after the share stopped.** The camera has the same structure (cameraLayerSync.ts:19-20).

**Camera gaps from the #824 review.**

- **Note 2 (unused clones after a reconnect without layer lines) is closed.** `dropMissingSenderClones` runs before the early return (cameraLayerSync.ts:51-52). The sync is now triggered after such a reconnect (peer.ts:244). Mutations M3b and M8 catch the loss of either part.
- **Note 1 (a line no longer fed keeps its clone) is closed as well.** A test now pins it (useWebRTC.cameraLayers.test.ts, "stops a lower layer's clone when the capture becomes too small"). Mutation M6 is caught.
- The #824 property "a reconnect reuses the same clones" still holds. The drop only runs for slots without a sender, and the sync runs after the rebind. The existing test still passes.

## 2. Side effects

- **`retuneForCapture` stops the clones before the re-sync.** The lower senders then sit on ended tracks until the queued chain reaches `feedLayer`. That wait covers anything already queued, plus one `setParameters` on the best line and one per lower line.
  - In the normal case this is milliseconds. The capture's size just changed, so the encoders reconfigure anyway.
  - The SFU moves an automatic viewer only after `adaptStall` (2 s, internal/sfu/adapt.go:61, viewer_track.go:217-229). A gap that long would need a slow `applyConstraints` queued ahead.
  - Stopping each clone inside the chain, right before its line is fed again, would remove the gap (note 2).
- **The changed condition in `finishOfferNegotiation` (peer.ts:241-246).**
  - `bound.screen` and `bound.camera` are true only when the best line was bound fresh on this connection and a share or camera runs (senders.ts:137-145). That is the reconnect case, and it is cheap: with no layer lines, `runSyncLayers` returns after the drop.
  - The `*LayerClones.some(Boolean)` terms are true during every share or camera with layer lines. So every server renegotiation of the same connection (joins, leaves) now runs a full screen sync and a full camera sync. That is up to six `setParameters` calls, because `tuneSender` does not skip unchanged values (senderTuning.ts:72-81).
  - Nothing behaves wrongly: the values are the same, and `declareLayers` deduplicates (layers.ts:100). But it is needless work on every renegotiation.
  - The only case those terms add beyond `bound.*` and `fresh.*` is a reconnect whose best line could not be bound. Keying the sync on "this offer bound any sender fresh" would cover that without the per-renegotiation cost (note 3).
- **The best line is unchanged.** It still carries the capture itself (layers.ts has no clone at index 0, and the tests pin `screen.track === track`).

## 3. E2EE

- The lower screen senders come only from `bindTransceiver(conn, mid, null, SOURCE_SCREEN, i + 1)` (senders.ts:148-153). That call runs `mediaCall().protectSender` before it switches the line to `sendrecv`, and returns `null` when protection fails (:94-104).
- `st.layerSenders` is set only from that return value and reset to null with the connection (peer.ts:30).
- Clones are placed only in `feedLayer` (layers.ts:91), onto entries of a copy of `st.layerSenders` (:139). So every clone goes onto a sender whose transform was armed when it was bound.
- `replaceTrack` swaps the track and leaves `sender.transform` as it is. The source (screen) and the layer index are the same as before.
- An in-flight sync that still holds the senders of a connection closed by a reconnect puts a clone, at most, on a protected sender of a closed connection. Nothing goes out there.
- Conclusion: the lower screen senders are protected exactly as before, and no path puts a clone on an unprotected sender.

## 4. contentHint and later constraints

- **At creation:** `layerClone` copies `source.contentHint` (layerClones.ts:19), and a new test pins it.
- **Hint changed later:** not followed. This is the required fix.
- **Constraints applied later** (`applyScreenQuality`: `track.applyConstraints(trackConstraints(quality))`, senders.ts:76): a clone keeps the constraints it was cloned with.
  - The clones are recreated only through `retuneForCapture`. That runs when the capture watch sees new `width`/`height`/`frameRate` settings, after up to `CAPTURE_POLL_MS + CAPTURE_SETTLE_MS` (1.5 s).
  - A quality change that changes the delivered size or rate therefore converges after about 1.5 s. Until then, the lower plans are computed from the capture's settings while a clone may still deliver its old size.
  - The comment at layers.ts:164-165 gives constraints as the reason for the stop in `retuneForCapture`. Yet `applyScreenQuality`, the only place that applies constraints, does not recreate the clones itself (note 1).
- **Pre-existing, now wider:** `cleanupPeerConnection` stops the capture watch (peer.ts:17), and the reconnect path (`startWaitingScreen`, peer.ts:183-192) does not start it again. Only `sendScreenVideo` does (screen.ts:76).
  - After a reconnect, neither the best line nor, now, the clones follow a resize or a quality change until the share is restarted.
  - This is not introduced here. With clones, though, it also leaves the lower lines on stale constraints (note 4).

## Notes (none blocking)

1. **Constraints reach the clones only through the capture watch.** After `applyScreenQuality`, the clones keep their old constraints until `retuneForCapture` fires (up to 1.5 s, and only if the settings change). Stopping the screen clones in the `applyScreenQuality` chain step also fixes the required item. The comment at layers.ts:164-165 should then name the right trigger.
2. **Freeze window in `retuneForCapture`.** The clones are stopped before the queued re-sync, so the lower lines carry ended tracks until the chain reaches them. This is short in practice, and well below the SFU's 2 s stall switch. Stopping each clone inside the chain, right before its line is fed, would close the gap.
3. **Needless sync on every renegotiation.** `screenLayerClones.some(Boolean)` and `cameraLayerClones.some(Boolean)` (peer.ts:241, :244) run both full syncs on every server renegotiation during a share or camera, with `setParameters` on unchanged values. A condition on "this offer bound a sender fresh" covers the reconnect cases.
4. **Pre-existing: the capture watch is not restarted after a reconnect** (peer.ts:17, screen.ts:76). It predates this PR, but now the clones also keep stale settings after a reconnect. Worth a follow-up.
5. **Test gaps.**
   - M5: the replace test passes without the explicit stop, because `layerClone` swaps clones lazily. The test does not check that the old clones are stopped before the new capture is fed, nor the case where the sync after a replace aborts.
   - M7: no screen test checks that a line that loses its plan stops its clone. The capture runs anyway, so this is not an indicator leak.
   - M9: the screen side of the peer.ts condition is only unit-tested in `runSyncLayers` (layers.test.ts), not through a reconnect with fewer layer lines.
6. **Redundant stop.** `releaseLayers` stops each line's clone in `dropTrack` and then all clones again (layers.ts:64-68). Together with `dropMissingSenderClones` (:135), the second loop is never needed.
7. **Housekeeping:** the stale comments at state.ts:12 and :71, and the duplicate stop-all loop (section 6).

## R2.1 The required finding

**The fix has two parts.**

- **A new clone after every quality change.** The `voice.screenQuality` watcher now runs `stopScreenLayerClones` once `applyScreenQuality`'s chain step has settled, and then `syncLayers` (watchers.ts:73).

## R2.3 Does anything new break?

**peer.ts (finishOfferNegotiation).**

- **Reconnect with the same lines.** `bindPublishSenders` binds the new senders before `finishOfferNegotiation` runs. So `dropMissingSenderClones` sees bound senders and keeps their clones, and the sync on the freshly bound lines reuses them. The camera reuse test from #824 still passes.
