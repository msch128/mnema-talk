## Blockers

### B1. Every e2e job dies with exit 127 before a browser starts
- Where: `e2e/ci-install-deps.sh:31` (introduced by 4d16f933e), together with the `cd "$(dirname "$0")"` at `e2e/ci-install-deps.sh:13`.
- Scenario: the workflow runs `e2e/ci-install-deps.sh chromium webkit` from the repository root (`.github/workflows/ci.yml:847`, `:1030`). The script first changes into `e2e/`. `${BASH_SOURCE[0]}` is still the relative `e2e/ci-install-deps.sh`, so `cd "$(dirname ...)/.."` tries `e2e/e2e/..`, fails, the substitution is empty and bash runs `/scripts/ci-dns-fallback.sh`: "No such file or directory", 127, and `set -e` ends the script.
- Evidence: run 43053095684, step "Install browser system dependencies" fails with exit 127 in e2e-shard 1-4, e2e (firefox), e2e (webkit 1/2, 2/2). Reproduced locally with a two-file stub of the same layout.
- Consequence: no CI run of this branch has executed the Playwright suite on a commit that contains the Trusted Types change (earlier runs of the branch are older commits, cancelled or failed). The Firefox and WebKit behaviour under the new policy is therefore unverified.
- Fix: in `ci-install-deps.sh` the working directory is already `e2e/`, so call `../scripts/ci-dns-fallback.sh ...` there, or compute the root before the `cd`. `ci-audio-sink.sh:39` is correct as written (it never changes directory). At all three call sites append `|| true`: the fallback is meant to be unable to fail a job, but under `set -e` a missing or non-executable script does exactly that.

### B2. `make staticcheck` fails on a cold Go module cache, and takes the rest of backend-checks with it
- Where: `scripts/staticcheck.sh:23` (`go run "$tool" ... 2>&1`) and the "did not run cleanly" filter at `scripts/staticcheck.sh:34`.
- Scenario: when the module cache does not hold staticcheck yet, `go run honnef.co/go/tools/cmd/staticcheck@v0.8.2` prints `go: downloading ...` lines to stderr. They are merged into the output, match neither the finding pattern nor an indented detail line, and the script reports "staticcheck did not run cleanly" and exits 1.
- Evidence: run 43053095684, job backend-checks, step "staticcheck": seven `go: downloading` lines, `make: *** [Makefile:148: staticcheck] Error 1`. Every later step (unit tests, allocation gate, fuzz smoke, build, docs checks) is skipped. Locally, with a warm cache, `make staticcheck` exits 0, which is why it was not seen.
- This recurs on every cache miss (any `go.sum` change), so it is not a one-off.
- Fix: warm the tool once before the three runs and fail clearly if that does not work, e.g. `go run "$tool" -version >/dev/null 2>&1 || { echo "staticcheck could not be built"; exit 1; }`, or build it into a temporary directory with `GOBIN=... go install "$tool"` and call the binary (also three times faster). Dropping `^go: downloading ` in the `sed` would work too but hides less cleanly.

## Should-fix

### S1. The name `mnema-emoji-picker` is unclaimed until the picker is opened for the first time
- Where: `web/scripts/emojiPickerCsp.ts:74` (the policy is created at module scope of the lazily loaded picker chunk, `dist/assets/picker-*.js`).
- Scenario, verified in Chromium 157 against the built bundle served with the exact header: on the sign-in screen `trustedTypes.createPolicy('vue' | 'mnema-markdown' | 'mnema-script-url', ...)` is refused as a duplicate, `default` and any other name are refused, but `trustedTypes.createPolicy('mnema-emoji-picker', { createHTML: s => s, createScriptURL: s => s })` is **accepted**. Whoever creates it first owns a full pass-through for HTML and script URLs. When the real picker loads afterwards, its own `createPolicy` throws, the patch falls back to the plain string and the picker's `innerHTML` is refused: the emoji picker is broken for that page.
- Weight: it needs script that already runs on the page, so it is not an injection path by itself. It does make the documented claim ("only the four named policies can make a value a sink takes", SECURITY.md) untrue until the picker is opened, and `trusted-types` without `'allow-duplicates'` only protects names that are taken.
- Fix: create the policy at start-up in `web/src/lib/trustedTypes.ts` (same module that creates `mnema-script-url`) and let the patched `parseTemplate` import it (`import { emojiTemplatePolicy } from '@/lib/trustedTypes'` inside the patch text; the alias resolves in Vite). The policy object stays module-private. Add a unit test that the name is taken after the app module loads.

### S2. `mnema-script-url` accepts any same-origin address, not only the worker scripts the build produced
- Where: `web/src/lib/trustedTypes.ts:42` (`sameOriginScript`).
- What I tested (`web/src/lib/trustedTypes.test.ts`, run locally, plus reading the code): `https://elsewhere.example/worker.js`, `//elsewhere.example/worker.js`, `data:text/javascript,1` and `blob:null/...` are refused; a `blob:https://<own host>/...` address is refused too, because its protocol is `blob:`. Any same-origin path, for example `/api/...`, is turned into a TrustedScriptURL.
- Mitigations in place: `ownScriptUrl` is reachable only from module code, uploads and link-preview images answer with `default-src 'none'; sandbox` and `nosniff`, `worker-src` is `'self' blob:`.
- Fix: accept only `/sw.js` and paths under `/assets/` (`url.pathname === '/sw.js' || url.pathname.startsWith('/assets/')`), in addition to the scheme and host check. The three call sites pass exactly those.

## Notes

- **N1. `vue` is a pass-through, so `mnema-markdown` enforces nothing by itself.** In the bundle Vue's `patchProp` runs every `innerHTML` value through its own policy (`e[t] = t === 'innerHTML' ? vuePolicy.createHTML(n) : n`), including the TrustedHTML from `mnema-markdown`, which is stringified and wrapped again. Any `v-html`, `:innerHTML` binding or `h('div', { innerHTML })` therefore passes. The commit says so honestly (middleware.go:220-223, SECURITY.md). The lint rule `vue/no-v-html` covers the directive only; a bound `innerHTML` prop is not covered. Optional: add a restricted-syntax rule for `innerHTML` in templates and render functions. The policy `mnema-markdown` itself is tight: its only rule calls `renderMarkdown(source, options)`, it has no `createScriptURL`, and the object is module-private.
- **N2. `DOMParser.parseFromString` is a Trusted Types sink**, contrary to the brief: Chromium refuses it with "This document requires 'TrustedHTML'". It does not matter here: neither `web/src` nor the bundle outside the API docs chunk calls it.
- **N3. Dead sink in the bundle:** highlight.js's `highlightElement` (`e.innerHTML = i.value`) is bundled in `typingTarget-*.js` but never called; the app only uses `hljs.highlight(...)` and sanitises its string (`web/src/lib/markdown/highlight.ts:84`). If someone calls `highlightElement`/`highlightAll` later it will throw under the policy.
- **N4. `loadtest/viewer/main.go:252`:** `err.Error()` is now called without a nil check. Correct today (`run` and `readLoop` in `session.go` return only non-nil errors, I read both), but a later `return nil` becomes a nil dereference in the load-test tool instead of a quiet exit.
- **N5. The fallback script overwrites `/etc/resolv.conf`** when `resolvectl` is missing or fails; on the hosted runners that file is a symlink into systemd-resolved's runtime directory, and `tee` writes through it. Fine for a throwaway runner.
- **N6. Local load test artefact:** my own picker test fetched emoji data from jsdelivr and was blocked by `connect-src`; that is my bare `<emoji-picker>` without the app's `dataSource` (`EmojiPicker.vue:68` passes a bundled file), not a finding.
