## BLOCKER

**B1. The masked-link destination length cap is a client end the server does not model.**
web/src/shared/lib/markdown/inline.ts:227 (`destination`): the client reads the target of `[text](url)` (and
`[text](<url>)`) for at most `MAX_LABEL * 4` = 2000 UTF-16 code units and then cuts it; when what follows the
cut is a valid tail (a title in quotes or parentheses and `)`), the link is rendered with the cut URL. If the
cut falls inside the authority, the client opens the host up to the cut. internal/automod/linkends.go:62-80
(`clientEnds`) knows the framed ends at each `)` and at the end of the authority, but not this one, so the server
reads only longer hosts. When those longer readings end in a character no DNS label has, the allow list ignores
them (compile.go:136, the `reachable` rule), and the block list does not find the listed domain in them
(they are not a subdomain of it). Measured:

- Server, real message route (temporary integration test in internal/server, same fixture as the fix's tests,
  ordinary 30-day member): a message of 2008 characters, ASCII only, posted under `allow_list allowed.example`
  and under `block_list other.example`: **201 in both**.
- Client, current bundle (`renderMarkdown` in Node 24 and the same href in headless Chromium 158): an `<a>` whose
  host is a subdomain of other.example. With the older bundle (user info not refused) a second form with a user
  name also works. Block-all and the new-account rule still refuse (any link counts).
- The current bundle's `plainAuthority` does not stop it: the padding that brings the authority to the cap can
  be made of percent-escaped characters that UTS #46 maps to nothing, and linkAuthority.ts:14 checks the raw text
  for Cc/Cf, not the decoded host.

Neither the hand-written cases nor the generator (linkParity.fixture.ts WRAPS: destinations are always short)
reach the cap, which is why 12,000,000 generated messages found nothing. The exact message is withheld from this
public report and was given to the coordinator.

Fix direction (server side is required, older bundles have the same cap; inline.ts is unchanged by this
commit): when a token is framed by `](` or `](<`, add an end at the position 2000 UTF-16 code units after the
destination start when it falls inside the authority (or simply treat a framed authority longer than that as
opaque, which no ordinary link reaches). Optionally also make the client drop a destination that hits the cap
instead of cutting it. Add a long-destination case to the cases fixture and the generator.

## SHOULD-FIX

**S1. The cost claim is wrong by an order of magnitude; work per message is quadratic.** The commit message says
hostile 4000-character messages take at most ~150 us. My own worst cases (`links()` directly, Apple M-series,
`-benchtime 100x`), new against old code (adc32bacc~1):

| input (at most 4000 characters) | new | old |
|---|---|---|
| one authority of 3960 non-ASCII letters, 15 `*` closers at its end (16 IDNA readings of the whole host) | 1.59 ms | 0.25 ms |
| 280 nested `https://a`, then 1480 trailing `.` (each nested scheme trims the shared tail again) | 1.07 ms | 0.06 ms |
| 40 nested links, each a 40-letter non-ASCII host with 15 closers | 0.97 ms | 0.08 ms |
| 2000-character token of `.,;:!?*_~|` runs | 0.03 ms | - |
| the author's own hostile set (BenchmarkMatchesLinks) | 57-109 us | - |

There is a bound (at most 16 readings per authority, one shared token end per run of nested schemes), but it is
O(schemes x token length) and O(16 x host length x IDNA). Not a blocker at ~1.6 ms per message with the posting
rate limits, but: correct the claim, and note that the new-account rule calls `links()` again
(engine.go:238, 246), so a server with the Links rule and the default new-account rule does the work twice.
Suggested: compute `links(content)` once per Check, and trim the shared tail once per token instead of per
nested scheme.

**S2. The PR-time parity test only renders as the older bundle (linkParity.test.ts:21 mocks `plainAuthority` to
true), but the current bundle is not a subset of the older one.** When `plainAuthority` refuses an outer link
(user info), the client goes on scanning and links a nested URL inside it, which the older bundle swallowed in
the outer href. The server judges every nested scheme, so it holds today, and the nightly sweep runs
`LINK_SWEEP_CLIENT=current`. But the smoke test should check both renderings (run the AGREED and generated rows
twice), otherwise a regression in nested judging that only the current bundle exposes is found a day late.

**S3. linkAuthority.ts checks the raw authority, not the host the browser reads.** `%E2%80%8B` (zero width
space), `%C2%AD` (soft hyphen) and every other percent-escaped invisible character pass `plainAuthority`,
the browser decodes them and IDNA maps them away (measured: `https://othe%E2%80%8Br.example` is linked and opens
other.example). It is defence in depth only (the server holds without it), but the stated purpose "none with a
control or invisible format character" is not met; decode the authority (or compare against
`new URL(raw).hostname`) before the test. This is also what B1's current-bundle form uses.

## Over-blocking (main product risk)

Method: 71 realistic messages of my own (search result URLs, Google/Facebook/YouTube redirect links, web archive
and archive.ph URLs, Wikipedia URLs with parentheses, URLs followed by punctuation, inside quotes, after emoji,
in `<...>`, masked links with titles, non-ASCII paths, IDN hosts, lists, quotes, spoilers, code spans and fenced
code), judged by the real `matchesLinks`, rendered by the real client.

- Allow list of 7 common domains (github.com, wikipedia.org, youtube.com, youtu.be, google.com, reddit.com,
  stackoverflow.com): the server refuses 21 messages; old code 19. The 2 new refusals are both redirect-style
  links whose opened host is allowed (`youtube.com/redirect?q=https://<unlisted>`,
  `translate.google.com/translate?...&u=https://<unlisted>`). One more refusal (also in the old code) is a URL
  inside a fenced code block, which the client does not link. With a wide allow list (20 domains) 4 of 71 are
  refused, all nested or code.
- Block list of 6 domains: server refuses 5, old code 1. The 4 new refusals all have a blocked host only inside a
  query or path (`archive.ph/https://<blocked>`, `youtube.com/redirect?q=https://<blocked>`,
  `accounts.google.com/...?continue=https://<blocked-subdomain>`, a translate link). The old one is code.
- Percent-encoded nested URLs (`?u=https%3A%2F%2F...`) are not judged, so most Google/Facebook/Bing redirect
  links still pass; only literal nested URLs are refused.
- Also refused although the client links nothing there: a URL in the title of a masked link
  (`[x](https://allowed.example "https://other.example")`), `www.` tokens (unchanged), code spans and blocks
  (unchanged), a URL whose port has a sign or whose host is empty (harmless).
- Nothing in the list was refused for parentheses, punctuation, emoji, IDN, non-ASCII paths, `@` in a path
  (`medium.com/@user`), Markdown around the link, or angle brackets. Opaque (more than 16 ends) was never hit by
  an ordinary link: it needs 17 closers inside one authority.

Is judging nested URLs needed for the property? Only where the client can link the inner URL: when the outer
link is not linked (a reading rejected or not exact, user info or a hidden character in the current bundle, an
outer `www.` token, a word character before the outer scheme), or when a place the client can end the outer
link (a Markdown closer, `||`, a framed `)`) lies between the two schemes. Otherwise the inner URL is part of
the outer href and the client never opens it on its own. A narrower rule that keeps the property: judge a nested
scheme only in those cases. It is more code in the hottest and riskiest spot; the current rule is safe and
documented (doc/moderation.md:345 now says so explicitly).

- Must change before merge: nothing on over-blocking.
- Owner's decision: keep "every nested http(s) URL is judged" (about 3% of ordinary links refused under an allow
  list, about 6% under a block list in my sample, all redirect-style), or take the narrower rule above. For a
  block list, refusing `archive.ph/https://<blocked>` may even be wanted (it shows the blocked page).

## The "opaque" and "unreachable host" rules

- Opaque (linkends.go maxEnds): only ever adds a refusal in every mode; truncating the ends list sets the flag,
  so it cannot drop a reading silently. Not a bypass. A denial of ordinary messages needs 17 closers inside one
  authority; none of my realistic links came near. OK.
- Unreachable host ignored by an allow list (compile.go:136, helper `reachable`): on its own it is sound (I
  checked in Chromium 158 that hosts with `!`, `'` etc. in the last label stay as written and cannot resolve).
  But it turns every end mismatch between server and client into an allow-list bypass whenever the server's
  longer reading ends in such a character, where before the fix such a reading counted against the message.
  B1 is exactly that. Once B1 is fixed, keep the rule, but it raises the stakes of any future end mismatch;
  the generator should include long and framed destinations so the sweep can see the next one.

### B1 (destination cap): closed

- Through the real message route, ordinary member, temporary integration test: my round-1 message (masked
  form, current bundle) and the user-info form for older bundles, under `allow_list allowed.example` and
  `block_list other.example`: **400 in all four**. I also tried the angle-bracket framing `[x](<url>)`, and a
  variant one unit shorter whose cut falls in the title: 400 in both modes.
- The cut is counted from the same start as the client's count in every framing. The client's destination
  must begin with `http(s)://` (SAFE_HREF is anchored, and a leading space ends the destination, so nothing
  before the scheme is counted). `<` is skipped on both sides. The server counts from the scheme to the end of
  its own authority, which is never earlier than the client's, because the server's stop set holds every
  character the client's destination stops at. Where the server stops earlier (`"`, `<`, a control character),
  the client's cut URL holds that character and SAFE_HREF refuses it. A title is counted as part of the server's
  authority, which makes the check stricter, not looser.
- "Authority longer than the cap" is the right condition. If the authority (scheme included) is at most 2000
  units, the cut falls at or behind its end and the host is unchanged. Percent escapes are counted as written
  on both sides; the client decodes them only after the cut. Surrogate pairs are counted as two units
  (utf16Len), and a cut through a pair is refused (probe: refused in both modes). NUL is dropped first on both
  sides.
- The other client caps cannot move a link end to a place the server does not judge:
  - Label limit 500: a longer label is not a link, and its contents are parsed as bare links, which are judged.
  - Inline depth 6: past it, delimiters stay literal, which gives fewer client ends, and the server's
    readings are a superset.
  - 400-character title window: if the title is longer, the masked link fails and the destination is parsed
    as a bare link, which the server's framed ends already cover (`trimClient(bare)`).
  - 6000-character render cap: unreachable within the 4000-character message limit, except with astral
    characters, where the client then links nothing (over-blocking only).
  - Probes for all four: refused where the client links other.example, in both bundles.
- My round-1 probe sets rerun on this commit, with only resolvable hosts counted: no bypass in any mode
  (block-all, allow list, block list) in either bundle. That covers 110 bypass-family inputs, 60,000
  own-fuzz messages and 21 new cap probes.
