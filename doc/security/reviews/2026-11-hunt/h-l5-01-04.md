## A. msch128/fix-h-l5-04 (6e13835db)

The design works like this:

- A post locks its channel row (`FOR NO KEY UPDATE`) first in `messages.insertMessageTx`, then draws its number.
- It writes that number to `channels.last_message_number` (migration 0103).
- `GET /api/read-state` reads the mark in the same statement as the counts.
- The client:
  - does not count a `message_create` at or below the mark;
  - adds back the messages above the mark that it counted while the request was on its way;
  - keeps only the newest answer.
- Followed threads replay the follow changes that arrived while the list was on its way.

### Must fix

**FIX-1 (BLOCKER for the merge, not for the design): no test detects a missing lock.**
The commit's test (`TestTheReadStateCountsExactlyTheMessagesUpToItsMark`) says it does not, and that is true.

Why it misses it: the new `UPDATE channels SET last_message_number` comes right after the insert. It already serialises
the posts of a channel from the insert to the commit. So without the explicit lock the only gap is between `nextval`
inside the INSERT and that UPDATE: a few microseconds, which random writers never hit.

I wrote a deterministic test that hits it: `fixreview-H-L5-04-lock-probe.go.txt` next to this report, an integration
test for internal/server. It works like this:

1. A test transaction holds a thread root `FOR UPDATE`.
2. Post 1 is a reply under that root that mentions the reader. It draws its number, then waits in its INSERT on the
   foreign-key share lock of `parent_id`.
3. Post 2 is a root message in the same channel that mentions the reader.
4. The reader takes GET /api/read-state.
5. After the held lock is released, the test checks that the answer's mention_count equals the number of mentioning
   messages numbered up to its mark.

Results:

- **Without the lock line:** fails 3 of 3 runs: `answer counts 1 mentions but 2 mentioning messages are numbered up to its mark 3 (one was still open)`.
- **With the fix:** passes 4 of 4 runs.

It needs only the existing harness (`newApp`, `a.db`, `register`, `readState`). The probe has debug logging of
`pg_locks`, which should be dropped when it goes into the branch. Add it, or an equivalent, to the branch.

**FIX-2 (coordinator): migration number.** H-L10-05 also adds a 0103.

- Whichever is renumbered needs its file name and its doc/upgrade.md table row changed together.
- Nothing else pins the name.
- The checksum is recorded per file name, so renumbering before release is safe.

### Checked, no defect

**(1) Every writer takes the lock and writes the mark.** `INSERT INTO messages` appears once in production code
(`internal/chat/messages/messages.go:365`, `CreateMessage`). `CreateMessage` has one production caller,
`insertMessageTx`, which `insertMessage` and `InsertMessage` wrap. Every path goes through it:

- `Service.Post`: the HTTP route, slash commands, bot API, scheduled messages (`internal/later/scheduled_send.go:138`)
- webhooks (`internal/webhook/handler_store.go:43`)
- uploads (`internal/media/handler_upload.go:126`)
- forwards (`internal/chat/messages/forward.go:182`)
- forum posts (`internal/chat/forum/forum_posts.go:76`)
- polls (`internal/poll/service.go:62`)
- Talk invites (`internal/chat/talks/talks_invite.go:62`)
- conversation call cards (`internal/chat/dm/dm_calls.go:353`)
- bot interaction responses (`internal/bot/interactions_respond.go:183`)

The Discord import creates no messages. `internal/chat/chattest/member.go:44` is test-only. No code moves a message to
another channel or renumbers it.

**(1b) The proof.** Numbers come from one global identity sequence (with no cache), plus a downward sequence for
conversations.

- Within a channel, the lock is held from before `nextval` until the commit. So the messages of a channel commit in
  number order.
- ReadStateSQL is one statement, so one snapshot. The mark `M` it reads was written by the transaction that drew `M`.
- Every lower-numbered message of that channel drew its number while holding the lock earlier, so it had committed or
  rolled back before `M`'s transaction got the lock.
- A higher number would have overwritten the mark had it committed.

The argument holds. Conversations are not in GET /api/read-state (`WHERE c.type <> 'dm'`), so their downward numbers
never become a mark. The Talk chat of a conversation draws public numbers and behaves like a channel.

**(2) Migration 0103.** It is a new file only; no applied migration is edited.

- `ADD COLUMN ... NOT NULL DEFAULT 0` takes no rewrite (fast default).
- The backfill is one grouped pass over `messages`.
- Migrations run in one transaction each, with no statement timeout, under the advisory lock (`internal/db/db.go:250`).

Measured with the real migrations 0001..0102 applied in a scratch schema, then 0103 timed (probe in
`fixreview-H-L5-04-measure-probes.go.txt`):

| messages | channels | 0103 duration | wrong marks after backfill |
|---|---|---|---|
| 1,000,000 | 200 | 109 ms | 0 |
| 10,000,000 | 200 | 4.4 s | 0 |

- **Locks.** `ALTER TABLE` holds an ACCESS EXCLUSIVE lock on `channels` for that time. The documented upgrade stops the
  app first (doc/upgrade.md: "Stop the app before changing its image or database"). Migrations are forward-only, and
  newer binaries refuse to start on a database migrated by a newer version.
- **Rolling update.** None is supported. If an old binary still wrote messages after the migration (against the docs),
  its posts would not move the mark. The mark would stay low until the next post from the new binary, and only answers
  that cross a live event could count a message twice. It heals by itself.
- **Down path.** The repo has none; rollback is restoring the backup.

**(3) Lock order and deadlocks.** The new lock (`FOR NO KEY UPDATE`) conflicts with other posters, `FOR NO KEY UPDATE`,
`FOR SHARE` and `FOR UPDATE` on the row, and plain `UPDATE channels`. Before the fix a post held only the foreign-key
`FOR KEY SHARE`.

I read every explicit lock and every `UPDATE/DELETE` on channels and messages:

| Path | Outcome |
|---|---|
| Pins (`pins.go:174`), webhook creation (`webhook/store.go:212`), outgoing webhooks (`outgoing_store.go:181`) | Lock the channel row first: same order. |
| Conversation gate (`dm_gate.go:92`) | Upgrades to `FOR UPDATE` in the same transaction: fine. |
| L7-06 member add (`dm_members.go`, branch msch128/fix-h-l7-06) | Locks the conversation row first, then reads: same order. |
| Message delete and edit (`message_mutations.go`), bulk delete (`moderation.go:219`), auto-delete (`auto_delete.go:221`) | Lock messages and never the channel row afterwards: no cycle. |
| Channel delete, layout, discordimport undo | Lock channel rows and wait behind a running post. Short; no cycle found. |

**One new cycle, found by reading, not run (NOTE):** account erasure
(`internal/auth/account/account_erase.go:82`) does three things in order:

1. locks the user `FOR UPDATE`;
2. later runs `UPDATE channels SET leader_id = NULL WHERE leader_id = $1` (and `dm_created_by`);
3. meanwhile, a post in a temporary Talk led by that user, mentioning them, holds the channel row and waits for
   `FOR KEY SHARE` on the user's row (the `message_mentions` foreign key).

PostgreSQL detects the deadlock after `deadlock_timeout` and aborts one side: the post or the erasure fails once.

- It is rare (the Talk's leader erases their account while being mentioned in it).
- The `dm_created_by` case existed before, through the conversation gate's lock.

Acceptable for a patch; worth a line in the code comment.

**Network calls.** None run inside the posting transaction. Automod runs before it. The upload's object is stored
before it; inside are only the media row and usage. Webhook files are inserted as rows only.

**Throughput.** Measured with `messages.InsertMessage` directly (no HTTP, no rate limit) on a loaded machine
(load 8 to 11), two runs each:

|---|---|---|---|---|
| 1, one channel | 364 / 641 | 2.1 / 10.7 ms; 1.3 / 4.5 ms | 533 / 248 | 1.6 / 5.7 ms; 3.2 / 18.5 ms |
| 8, one channel | 659 / 628 | 8.3 / 51.9 ms; 8.8 / 54.8 ms | 480 / 226 | 15.5 / 38.7 ms; 27.5 / 388.6 ms |
| 32, one channel | 364 / 319 | 64 / 379 ms; 68 / 623 ms | 348 / 286 | 82 / 256 ms; 93 / 389 ms |
| 8, one channel each | 569 / 519 | 10.4 / 57 ms; 11.7 / 65 ms | 345 / 393 | 14.4 / 119 ms; 14.1 / 106 ms |
| 32, one channel each | 320 / 415 | 65 / 576 ms; 58 / 323 ms | 319 / 398 | 71 / 464 ms; 63 / 317 ms |

- **Busy channel:** with 8 concurrent writers in one channel, throughput falls by roughly 25 to 65 % and p50 latency
  roughly doubles.
- **Spread over channels:** within noise. Something global (the per-statement message-count trigger or the pool)
  limits both sides alike.
- **In practice:** a channel still takes a few hundred posts a second, far above what the per-member send rate limit
  lets real members produce.

**(4) No leak.** GET /api/read-state drops channels the caller cannot view (`handler_readstate.go`,
`visibleReadStates`). ViewChannel includes the history, and the mark is the number of a message the caller can already
read (every message_create and history row carries it). Conversations are excluded, so the downward conversation
numbering of migration 0050 stays private.

Side note: the backfill sets a conversation's mark to max(number), its *oldest* message, because conversation numbers
count down. The post path writes its newest. Both are unused because conversations are excluded. NOTE: say so in the
migration comment.

**(5) Compatibility.**

- An old client against the new server: the 3.0.9 decoder `isChatReadState` ignores unknown fields.
- A new client against an old server: the field is optional; the answer is applied as before. My own case below shows
  a later event still counts.
- Two tabs: each tab has its own state. A read in the other tab arrives as `read_state` with counts, and
  `noteReadStateCleared` keeps it against an older answer.
- OpenAPI: the field is added as optional. The commit says openapi-diff shows no breaking change; I did not rerun
  contracts-check (see "Not run").

**Own cases (temporary vitest on the storeLists harness, 4 of 4 pass):**

1. A mention and a plain message cross a held answer: both are added back, [3, 1].
2. A thread reply that mentions me, delivered before an answer that includes it, counts once.
3. A read in another session while the answer is held keeps the read.
4. An answer without a mark is applied as before, and a later event counts.

## B. msch128/fix-h-l5-01 (2e22972c2)

The design: after a delete, a bulk delete, the auto-delete sweep or an edit, `readstate.Recount.Tell` sends
`read_state` with counts (`wire.ReadStateCounts`). It goes to online members who may view the channel and whose read
marker lies before the changed messages; for an edit, only those mentioned before or after.

### Must fix

**FIX-1 (BLOCKER): Recount costs one read-state query per online member, and the request waits for all of them.**

- `Tell` runs on the request goroutine before `DELETE` answers 204 (`handler_messages.go`), and the same goes for the
  bulk delete.
- It runs `ChannelReadState` (the full ReadStateSQL for one channel) once per online member who is behind.
- Measured with `readstate.Recount` against the real database, every member online and behind (probe in
  `fixreview-H-L5-01-probes.go.txt`):

| online members | unread backlog in the channel | Tell duration | events |
|---|---|---|---|
| 1,000 | 50 | 0.25 s | 1,000 |
| 1,000 | 5,000 | 4.4 s | 1,000 |
| 10,000 | 500 | 6.8 s | 10,000 |
| 10,000 | 5,000 | 39.6 s | 10,000 |

The docs size the server for 10,000 members (doc/architecture.md "Unread tracking with 10,000 members"). At that size,
deleting one message makes the deleter wait up to 40 s, and one database connection stays busy all that time. Required:

- Run Tell off the request path, in a bounded worker like the follow sync, after the broadcast so that the order to each
  connection is kept. Use a context that survives the request: today a client that closes the request cancels
  `r.Context()`, and the recount silently stops part-way.
- Compute all members' counts in one query, or a few batches, instead of one per member.
- Auto-delete calls Tell once per batch of a run (`sweepBatch`). Call it once per channel and run.

**FIX-2: the sweep path is untested.** The tests build `AutoDeleter` without `Recount`, so the sweep path never ran
under test.

- My test (`TestReviewSweepTellsTheReader` in the probe file) ages a mentioning message by 10 days, sets 7-day
  auto-delete, sweeps with `Recount` wired to the hub, and expects `read_state` counts [0, 0].
- It passes on the branch and fails (`no read_state with counts`) with the `Tell` call in `auto_delete.go` removed.
- Note that it must move the reader's sign-up back, or the aged message is never unread.

Add it, or an equivalent.

**FIX-3 (small):** the comment of `TestARecountSkipsWhoReadTheChannel` says "and neither is one who cannot see the
channel", but the test does not check that. Either test it or drop the claim. By reading, the code fails closed: it
checks `snap.Channel(...).Has(ViewChannel)` for each member, and if the snapshot errors nobody is told.

### Recount cost

My probe now drives `readstate.NewRecounter` with every member online and behind. "Worker" is the time from Tell until
the worker is idle; "small" is how long a one-member channel queued right after the big one waits.

| Online members | Unread backlog | Tell (caller) | Worker | Small channel told after |
|---|---|---|---|---|
| 1,000 | 50 | 1 µs | 28 ms | 26 ms |
| 1,000 | 500 | 1.3 µs | 189 ms | 194 ms |
| 1,000 | 5,000 | 5.5 µs | 2.19 s | 2.15 s |
| 10,000 | 500 | 1.8 µs | 1.88 s | 1.85 s |
| 10,000 | 5,000 | 1.6 µs | 21.6 s | 18.7 s |
| 500 (one statement) | 50,000 | 1.3 µs | 4.9 s | 4.9 s |

- **The delete and the bulk delete** no longer wait: Tell takes microseconds. The worker's times match the author's
  (1.97 s / 20.5 s).
- **Head of line (NOTE):** with one FIFO worker, a big recount delays the corrections of every other channel. Meanwhile
  a member sees the stale badge, which is exactly the 3.0.9 behaviour, until the recount arrives or they read the
  channel. A late recount is still correct: it is computed when it runs, and it carries the mark of that moment.
  Requests for a waiting channel merge, so one channel never has more than one job waiting.
- **Abuse (NOTE):** a member can keep the worker busy by deleting their own messages in many big channels. The cost is
  bounded: one database connection at a time, and at most 256 waiting channels. Further channels are skipped and logged,
  and their badges then behave as in 3.0.9. I accept that.
- **Database (NOTE):**
  - Each statement reads under a snapshot with ACCESS SHARE locks only; no row locks.
  - A 500-member statement takes about 1 s at 5,000 unread messages and 4.9 s at 50,000 (the documented capacity case).
  - From about 150,000 unread messages, a statement would hit the 15 s `DB_STATEMENT_TIMEOUT`. The recount is then
    logged, and the badges behave as in 3.0.9.
  - The 2-minute cap per recount works the same way: batches finished before it are sent, the rest is not.
- **Shutdown:** I cancelled the context during a 10,000 × 5,000 recount.
  - The worker stopped at once: the running statement is cancelled through its context, and `Wait` returned in under
    1 ms.
  - A Tell after the cancel is refused (`r.ctx.Err()`).
  - `Router.Close` cancels first and waits at most `jobsStopWait` (10 s), so a 2-minute recount cannot hold it.
