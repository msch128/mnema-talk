# Fix review H-L6-01 (forum audit entries of a private forum reach every auditor)

Reviewer: fix reviewer, independent of the finding and the fix. Read-only: nothing in the repository changed, nothing pushed.
Fix: branch msch128/fix-h-l6-01, commit 6e4164178 (`fix: class the forum audit entries by channel and hide actions without a class`), on the lane 6 test commit 6f0cd798e, base origin/main f58bc3fc6 (3.0.9). Only 6e4164178 was reviewed.
Inputs: findings/H-L6-01.md, reviews/repro-H-L6-01.md, reviews/refute-H-L6-01.md.

## Verdict: MERGE AFTER FIXES

The fix removes the cause for every variant the finding and the refuter list (forum.post_update, forum.tag_create/update/delete, forum.settings_update, forum.tag_reorder) and also the second cause the author names (a catch-all that failed open). The class change is exactly the intended one: of the 139 actions the server can write today, only the six forum.* actions changed class (Auditors to Channel), nothing widened, and the SQL and Go agree on every action for every viewer kind on a real database. The blocking item is in the new structural test, not in the production change: it claims to find every writer, but it is blind to an aliased import of the audit package, a type alias of audit.Entry, and any raw `INSERT INTO audit_log ... VALUES ($1` anywhere in the tree, which together defeat the very guarantee doc/moderation.md now promises ("A test reads the server's source for every action an entry can be written with"). That is a SHOULD-FIX (the production behaviour already fails closed through the new catch-all, so a missed writer is hidden, not leaked); I list it as the condition for merge because the documentation states the test as a guarantee.

No BLOCKER.

A dynamic action (`admin.*`, `event.talk_*`) was probed with a concrete suffix.

Result: old ClassOf, old SQL and new ClassOf agree for 133 actions. Six changed, all Auditors to Channel:

Every forum.* writer sets `Entry.ChannelID` to the forum (internal/chat/forum/handler_forum.go:300, handler_forum_extras.go:121 and :178, handler_forum_tags.go:208-209 for create/update/delete), so an auditor who can view the forum keeps reading them; the fix's integration test shows that for a Staff auditor and the Owner.

So no stored row of a real deployment changes class except the forum ones.

## 4. The structural test (internal/audit/actions_scan_test.go)

What it catches (each tried with a planted writer in a scratch package, deleted afterwards): a new `audit.Entry{Action: "x.y"}` with no row (reported); `Action: fmt.Sprintf(...)` (fails closed: "cannot tell which action"); `Action: m["k"]` (fails closed); `var action = "x.y"` inside the function (fails closed; DeclStmt is not followed, the error is the safe outcome); an exported helper in another package with the action as a parameter (fails closed, see NOTE 4).

What it misses (planted, the test stayed green):

- SHOULD-FIX 1, import alias. `import aud ".../internal/audit"` with `aud.Entry{Action: "secret.alias"}`: `isEntryType` compares the selector's package identifier with the literal string `audit` (actions_scan_test.go:132), so an aliased file is invisible in full, including the writers that would otherwise fail closed (Sprintf, map lookup). Fix: resolve the local name of the audit import per file from `f.file.Imports` (the alias or `audit`) and compare with that; also treat a dot import.
- SHOULD-FIX 2, raw INSERT with a parameter action. `q.Exec(ctx, "INSERT INTO audit_log (action, ...) VALUES ($1, ...)", "secret.rawparam")` anywhere: rawInsert exempts every string containing `VALUES ($1` (actions_scan_test.go:173), meant for the writer's own INSERT at internal/audit/audit.go:96 but applied tree-wide. Fix: exempt only that file (or that one literal), report every other parameterised INSERT as "cannot tell"; also match case-insensitively (`insert into audit_log ... values ('secret.lower'` is missed: the `strings.Contains` at :168 and the regexp at :163 are case-sensitive).
- NOTE 1, type alias. `type E = audit.Entry; E{Action: "secret.typealias"}` is missed. Rare; resolving aliases needs go/types, or at least flag `= audit.Entry` alias declarations as an error.
- NOTE 2, entries not built from a literal: `json.Unmarshal(b, &e)` into an `audit.Entry`, then `Record(e)`, and `e.Action = "x"` in a file of the same package that does not import audit (the receiver's type is declared elsewhere) are missed; the scan looks at literals and imports-gated assignments only, never at the calls of `Record`/`RecordTx`/`RecordOrLog`. A sturdier closure: for every call of those three methods, require that the argument be followed back to a literal the scan has classified, and fail otherwise.
- NOTE 3, a call through a function value (`r := rec; r(ctx, l, "secret.indirect")`) is missed when the function also has one direct call: `arguments` counts calls by name only (actions_scan_test.go:316). With no direct call at all, it fails closed.
- NOTE 4, the cross-package helper fails closed for the wrong reason: a planted exported helper `Write(ctx, l, action)` produced "cannot tell" because `arguments` matches every call named `Write` in the tree (io writers with three arguments) and one of them is not a literal. Safe, but a reader will be told to "build it from string literals" when they did. Matching the package qualifier of the call would make it precise.
- Web-facing code: the web client has no database access; the only writers are in internal/ and cmd/, which the scan covers. Writers in *_test.go files are excluded on purpose.

Does it fail closed when it cannot follow a value: yes, for every value it reaches. It fails open for writers it does not recognise as writers (SHOULD-FIX 1 and 2, NOTEs 1 to 3). Because the production catch-all is now the narrowest class, a missed writer is hidden from auditors, not leaked, so these gaps are about the promise in the documentation (doc/moderation.md, "Access": "A test reads the server's source for every action an entry can be written with and fails for one without a row of its own"), not about a leak today. No aliased import, type alias, or second raw INSERT exists in the tree today (grep).

## 5. user.talk_kick (the author's open question)

Decision: it should change; it is not part of this fix's scope and need not block it.

The per-Talk disconnect (`POST /api/channels/{id}/voice/{userID}/disconnect`, internal/auth/memberadmin/users_admin_talk.go:105) writes `user.talk_kick` with the target member's name, the moderator as actor, the time, and `details.channel_id` = the Talk, without `Entry.ChannelID`. Under the Auditors class every holder of View audit log reads that member X was in Talk C at time T and was removed by moderator M, for a private Talk they cannot see. That is exactly the fact the voice.* rows are hidden for ("who was in which Talk", Channel class). The Talk is named by id only, and the id of a private channel is not otherwise readable to such an auditor (channel.* is Channel class), so the leak is presence of a named member in an unnamed private Talk: S4 territory, but inconsistent with voice.join/leave.

What should change: record the per-Talk disconnect under a Channel-class action with `ChannelID` set to the Talk (for example `voice.disconnect`, which `voice.%` already classes; add it to `auditKinds` in internal/moderation/history.go as `talk_removal`, whose output carries no channel), and keep `user.talk_kick` for the admin-wide kick (`POST /api/admin/users/{id}/kick`, internal/audit/routes.go:67), which names no Talk and is rightly Auditors class. Rows already stored keep their action (audit_log is immutable), so old per-Talk rows stay wide; say so in the changelog. Not verified at run time (it needs a live Talk); this is from the code.

## 6. Performance of the listing (200,000 generated rows, EXPLAIN ANALYZE)

The SQL of the old and the new filter was rendered with its arguments inlined (as a custom plan sees them) and run in the integration database on 200,000 rows after ANALYZE, best of five, viewer without privileges seeing one channel:

| scenario | query | old | new |
|---|---|---|---|
| actions uniform over the 139 | first page (51) | 0.24 ms | 0.50 ms |
| | page of 201 | 0.48 ms | 0.92 ms |
| | `action=forum` 201 | 0.88 ms | 4.7 ms |
| 90 % auth.login | 51 | 1.4 ms | 1.4 ms |
| | 201 | 3.1 ms | 4.4 ms |
| | `action=forum` 201 | 15.6 ms | 19.2 ms |
| nothing visible to the reader (full scan) | 51 | 66 ms | 169 ms |
| | 201 | 66 ms | 184 ms |
| | `action=forum` | 15-21 ms | 14-20 ms |

Index use is unchanged: the unfiltered listing walks `audit_log_pkey` backwards with the CASE as a filter and stops at the limit (old and new); the group filter uses the same parallel scan in both. The CASE costs about 2.5 to 3 times the old filter per row (it evaluates up to 90 WHEN branches, Auditors literals last), which shows only when the reader sees few rows and the scan has to go deep. NOTE 5: acceptable for an admin-only, paged route (worst case 0.18 s at 200k rows, linear beyond); if it ever matters, put the Auditors literals in one `action = ANY($n)` branch placed where they stand in the table, which keeps the first-match order and cuts the branch count by about half.
