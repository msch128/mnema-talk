Reviewer: independent reviewer of the fix. I filed the finding (as the reviewer of the H-L3-S1-01 fix) but did
not write this fix. Fix: branch msch128/fix-h-l3-12, commit 6be8b17fa on top of 33860ed91, reviewed alone.

## Verdict: MERGE AFTER FIXES

The fix removes the cause for a block. Every pair check asked `type = 'dm'`. Now the posting gate, the edit
check and the reaction and vote query resolve `channels.dm_id` to the conversation, so every write door of
the Talk's chat answers a block the way the conversation does. Groups, group Talks, server channels and
server Talks are unchanged (measured). The unread count change is correct and keeps the plan test green.
The docs say what is stopped and what is left.

One fix is needed before merge (SHOULD-FIX S1). The new rule lets edits through when the other member of
the pair was erased. That undoes the parent commit's behaviour for the conversation itself, and it is not
the "disabled or erased" rule that the code comment, the commit message and moderation.md ("follows the
same rule with the same answers") claim. It is a one-line condition. Nobody can read what is written there,
so it is not a blocker.

## Findings

### SHOULD-FIX

**S1. An erased other member no longer closes the conversation of two to edits, and never closed the Talk's
chat.** (internal/chat/messages/dm_gate.go, `checkPairWritable`: `if (!on && !talk) || active != len(others)
|| blocked > 0`.)

- Erasing an account deletes its `dm_members` rows (internal/chat/account/account_erase.go:52). The pair
  stays for the survivor, because it is not a sole conversation.
- `others` is then empty: `active` (0) equals `len(others)` (0), so the write passes.
- `checkDMReachable`, which the parent used for edits, also refuses `active == 0`.

Measured after erasing alice:

| Bob's write | Parent 33860ed91 | This fix |
|---|---|---|
| Post in the conversation | 403 | 403 |
| Edit in the conversation | 403 | **200** |
| Post in the Talk's chat | 201 | **201** |
| Edit in the Talk's chat | 200 | **200** |

This contradicts:
- the function's own comment ("the other side's account disabled or erased, refuses");
- the commit message;
- moderation.md's "the same rule with the same answers";
- the conversation's own post rule.

No one but the survivor can read these messages, so this is consistency, not exposure. Fix: refuse when
nobody else is there, e.g. `len(others) == 0 || active != len(others) || ...`. Add one cell (erase the
other side, then edit in the conversation and post in the Talk's chat: 403) next to
`TestNoEditReachesADisabledAccountInAConversationOfTwo`.

### NOTE

- **N1.** Once the Talk's chat answers 403 to everything, a pair Talk stays in the sidebar after a block with a
  chat nobody can write in, until it empties. This is intended (the refuter's direction) and documented. The
  web client may show a composer that always refuses there. That is UI, not examined.
- **N2.** `gatePost` skips the pair check for `nm.WebhookID != nil`. Webhooks cannot target a channel with
  `dm_id` (internal/webhook/handler.go:106 refuses it), so this is unreachable. The skip is consistent with
  `gateDM`, which refuses webhooks outright. A refusal there instead of a skip would fail closed. Optional.
