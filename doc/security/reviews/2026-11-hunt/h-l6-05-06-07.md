## 2. A hidden call answers like a missing channel

I posted `POST /api/events` 120 times per case, all as a holder of Manage events:

| Case | Status | Same bytes as a random id | Median | p10 | p90 |
|---|---|---|---|---|---|
| random id | 400 | (reference) | 0.48 ms | 0.38 ms | 0.69 ms |
| call Talk, caller is a member | 400 | yes | 0.60 ms | 0.46 ms | 0.84 ms |
| call Talk, caller is not a member | 400 | yes | 0.62 ms | 0.49 ms | 0.80 ms |
| text channel | 400 | yes | 0.46 ms | 0.38 ms | 0.62 ms |

- **Bytes.** Every case returns the same bytes. All of them return the shared `errNotATalk` value. A text channel and a missing id take the same path (one query). Before the fix, a non-member got 403 "you cannot view this Talk channel", which told them the id was a Talk. Now that answer is gone.
- **Timing.** A call Talk costs one more query: `talks.IsDMTalk` runs after `SELECT type`. In this run that is about 0.1 ms on every percentile, so it is not within the noise. It is an oracle only for someone who already holds the call's UUID (a random v4 id) and Manage events.
- **SF-3.** Fold the check into the first query (`SELECT type, dm_id IS NOT NULL FROM channels WHERE id = $1`). Then all refusals take one path, and the code is simpler.
- **Lookup errors.** A failed lookup returns the error (500), which fails closed.

## 3. Events that already name a call Talk

`events.channel_id` is declared `ON DELETE CASCADE` (migration 0070). Such events die with the call Talk, which goes when it is empty or with its conversation. So they exist only for calls that were running when the server was upgraded.

To test this I inserted one directly, since the API now refuses to create one:

- `PATCH` (title only): 400. The merged payload is validated, so the event can no longer be edited or moved out of the call. That is acceptable.
- A comment: 201, not audited.
- `POST /api/events/{id}/cancel`: 200, and it writes **`event.talk_cancel` with the call Talk's id and the title**. The Owner and Administrators outside the conversation read it. A non-member auditor does not.
- The event list does not show the event to outsiders.

**SF-1.** In `auditRecord`, skip the entry when `ev.ChannelID` is a conversation's call Talk, and fail closed on a lookup error. That covers cancel, cancel-following and any other path in one place. The alternative is to refuse cancel for such an event. The window is small, so this is a SHOULD-FIX, not a BLOCKER.

Older audit rows of this kind (`event.talk_*` naming a call Talk) stay readable by the Owner and Administrators, because the log is immutable. doc/upgrade.md could say so, as H-L6-03 did for its old rows.

## 6. The two paths the author did not fix: rename and duplicate a call Talk through the admin channel routes

Probed at 8c95e9466. The actors were an Administrator who is in a group conversation and, separately, a member who holds only Manage channels server-wide, inside their own conversation.

| Action | Result | What the Owner and Administrators outside the conversation read |
|---|---|---|
| `PATCH /api/admin/channels/{call}` `{"name": ...}` | 200 (Administrator); 200 (Manage channels only) | `channel.update`: actor, target "Talk 1", the call's id in params, and before/after/changes (name "Talk 1" to the new name). Owner and Administrators skip the class filter, so they read it. |
| `POST /api/admin/channels/{call}/duplicate` | 201 (both actors) | `channel.duplicate` with the call's id. A **permanent community Talk** named after the call appears in everyone's channel list. |
| `PATCH /api/talks/{call}` by a non-leader Administrator | 403 "only the Talk leader can change this Talk" | (nothing) |

The details hold the channel snapshot only: name, type, limits, category NULL. They hold no `dm_id`, no leader and no other member. What reaches the Owner is that the actor had a call Talk at time T, plus its id and name. The other members are not named.

**Judgement: a finding, S4.** It breaks two documented statements:

- doc/talks.md: "Nothing about it reaches the audit log (who joined it, **renamed it** or when it went)".
- doc/architecture.md: the administrative channel routes "answer 404 for a conversation id". The call Talk is meant to be "as private as the conversation".

S4 because it needs Manage channels or Administrator, and the actor mostly discloses their own participation. The duplicate also creates a community object from a private one.

H-L6-04 did not cause this: Manage channels is not a channel-scoped bit and was held in the call before. But since H-L6-04, a member without View channels who holds Manage channels can do it too.

Suggested fix: the admin channel routes (update, delete, duplicate, and any other route keyed by a channel id) should answer 404 for a conversation's call Talk, as they already do for the conversation itself, and as incoming and outgoing webhooks already do. I did not probe `DELETE /api/admin/channels/{call}` (`channel.delete`); it presumably behaves the same.

### The hideCallTalks middleware (9dbb9a667)

**What it does.** It sits on the /admin router, after `RequireAnyPerm` and before the audit middleware. For a `RoutePath` of `/channels/{uuid}[/rest]` that names a call Talk, it replaces the id in `rctx.RoutePath` with a fresh uuid before chi chooses the route. Handlers read `chi.URLParam` from that routing, so they see the fresh id.

**Path spellings.** Each spelling was sent for the call and for a missing id and compared by status and body. All 13 answer alike:

| Spelling | Answer |
|---|---|
| canonical | 404 "channel not found" |
| upper case | 404 "channel not found" |
| 32 hex digits without dashes | 404 "channel not found" |
| `urn:uuid:` prefix | 404 "channel not found" |
| a percent-encoded dash | 400 "invalid id" |
| a percent-encoded digit | 400 "invalid id" |
| trailing text after the id | 400 "invalid id" |
| `;x` after the id | 400 "invalid id" |
| `//` before or after `channels/` | 404 "route not found" |
| trailing slash | 404 "route not found" |
| `/../` | 404 "route not found" |
| `/./` | 404 "route not found" |

There is no bypass, for two reasons:

- The middleware parses the same string chi routes on. chi routes on `RawPath` when one is set, so an encoded id is never decoded on either side.
- The middleware and the handlers both use `uuid.Parse` from google/uuid. Every form one accepts, the other accepts too.

**What still holds the real id.**

- The audit middleware matches `r.URL.Path`, not the route context (internal/audit/middleware.go:59). Its route parameters and `captureBefore` therefore use the **real** call id and read the call's real snapshot before the handler runs.
  - No entry is written today: entries are written only for 2xx answers, and every route answers a missing id with 4xx. The author's ghost comparison and my probe confirm that; the Owner's audit log does not carry the call id.
  - A route that answers 2xx for a missing channel, for example an idempotent DELETE or a future GET-like POST, would write an entry with the real call id and the call's name from the before-snapshot.
- The request log records `LogPath(r.URL.Path)`, so the real id goes into the operator log. Operator logs are not a public surface and already hold call ids from ordinary member requests.
- Metrics use `RoutePattern()`, so their labels hold no id.

**SHOULD-FIX R2-1.** When the middleware swaps the id, also set `r.URL.Path` (and clear or rewrite `r.URL.RawPath`) on a shallow copy of the request. Then the audit middleware, `captureBefore` and the request log all see the fresh id too. It is two lines and removes the only route by which the real id could still reach the audit log.

**Lookup cost and failure mode.** Each admin request whose path starts with `/channels/{uuid}` costs one primary-key lookup, on reads too: about 0.1 ms. A failed lookup answers 500 before the handler and before the audit middleware, so it fails closed and records nothing.

**Middleware or guard?** A check inside the admin channel guard is **not** simpler. There is no single guard that answers 404 for a conversation. The conversation case is handled by `type <> 'dm'` in each store query, plus `Guard.Require(ViewChannel)` in four packages:

- chat/channels (rename, delete, duplicate, auto-delete);
- roles (overwrites);
- webhook (`authorize`, which already excludes `dm_id`);
- the layout check.

`Guard.Require` is shared with the member routes, where call Talks must stay visible, so it cannot simply learn about call Talks. A guard-based fix would need an admin variant in four packages and a promise that every future route uses it. The middleware also covers routes added later, and swapping the id gives byte-identical answers per route, where a fixed 404 would not (some routes answer 400 or 409 for a missing id). Keep the middleware, with R2-1.

**Admin routes that take a channel id outside the path:**

| Route | Behaviour for a call Talk |
|---|---|
| layout (body) | `checkChannelMove` refuses a call Talk as hidden. Revert check: without it, PUT layout answers 204 and the audit log carries the call id. |
| onboarding `start_channel_id` | requires a text channel, so a call Talk gets the same answer as a missing channel |
| outgoing and incoming webhooks | already excluded through `dm_id` |
| events and automod | round 1 |
| audit log `target_id` or `channel_id` filters | `GET /api/admin/audit-log?target_id=<call>` returns `{"entries":[]}` now. The Owner reads everything anyway, so the filter tells them nothing they could not read; old rows stay visible (NOTE R2-c). |

**Calls deleted on older versions.** DELETE on the base deleted a live call (204). The conversation stays, so nothing is left to clean in the data. Duplicates made from calls are ordinary community Talks that their makers created. The audit rows of earlier renames, duplicates and deletes (`channel.update`, `channel.duplicate`, `channel.delete` naming a call Talk) stay readable by the Owner and Administrators, because the log is immutable. NOTE R2-c: doc/upgrade.md should say so, as for H-L6-03. The author did not add an upgrade note.
