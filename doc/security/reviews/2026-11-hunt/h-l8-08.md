## What the fix does, and why the invariant is right

`vetAnswerCandidates` now calls `vetAnswerSSRCs` on the parsed SDP before any
candidate is counted and before `SetRemoteDescription`. The rule: per media
section at most one stream (one SSRC, plus the SSRCs an `a=ssrc-group` FID or
FEC-FR line ties to it); no SSRC in two sections; otherwise the whole answer is
refused (`SetAnswer` returns `errAnswerSSRCs`, `internal/ws/handle.go:209` logs
it at warn, the offer's watchdog resends).

Why one stream per section is correct, confirmed against the library source:
`trackDetailsFromSDP` (`sdp.go:79`) decides how many inbound tracks a section
has, and it reads only two attribute kinds to do so — `a=ssrc` and
`a=ssrc-group` (FID/FEC-FR, which demote the repair SSRC out of the track
list). For every track it then calls `startReceiver` →
`startReceive` (`rtpreceiver.go`), which opens an SRTP read stream per SSRC.
The SFU creates exactly one receiver per section, so a section the library
reads as carrying two streams makes the library start a receiver the SFU never
built, and the unguarded dereference follows. One stream per section is the
right invariant for the SSRC path.

Two caveats the fix does not fully honour (the blockers):

1. The library decides the number of streams from `a=ssrc`/`a=ssrc-group`, but
   it attaches each to a transceiver **by mid**. The rule never checks that
   mids are unique, so an answer can stay within "one stream per section" and
   still drive the library to two streams on one transceiver.
2. The library parses `a=ssrc-group` differently from the fix. The fix must
   read a group exactly the way the library reads it, or an answer the fix
   treats as a benign repair pair is treated by the library as a second
   independent stream.

The library does read `a=rid`/`a=simulcast` and session-level attributes, but
neither leads to the crash (see Confirmations), so the rule's silence on them
is acceptable.

## BLOCKER 1 — `a=ssrc-group` parsed more leniently than the library

`ssrcPair` (`internal/sfu/answer_candidates.go`) splits the group value with
`strings.Fields`, which collapses runs of whitespace and splits on tabs. The
library splits the same value with `strings.Split(attr.Value, " ")`
(`sdp.go:111`) and only demotes the repair SSRC when that single-space split
has exactly three fields (`sdp.go:117`, `:145`). The answer SDP that reaches
the library is the fix's own re-marshalled form, so the exact spacing the
client wrote is preserved through to the library.

Consequence: a FID group whose value is spaced so that the single-space split
is **not** length-3 (an extra inner space, a trailing space, or a tab) is read
by the fix as a valid repair pair (benign) and by the library as "no repair
pair" — so the library keeps the second SSRC as an independent stream, starts a
second receiver on the section, and the process ends.

Reproduced against the fix: three spacing variants of a FID group, each
accepted by `SetAnswer` (`err=<nil>`) and each followed by the
`rtpreceiver.go:544` nil-pointer panic that exits the test binary. Honest
answers are unaffected.

Suggested fix: parse the group exactly as the library does — split on a single
space, require length 3 and the `FID`/`FEC-FR` token — and refuse any group
value that is not exactly that shape. I made this one change
(`strings.Fields` → `strings.Split(value, " ")` in `ssrcPair`), rebuilt, and
all three spacing variants were then refused with `errAnswerSSRCs` while the
honest answer still connected and `TestAnAnswer*` still passed.

## BLOCKER 2 — two media sections sharing one `a=mid`

`vetAnswerSSRCs` checks SSRCs per section and cross-section SSRC uniqueness but
never checks that mids are unique. The library matches each section's tracks to
a transceiver by mid (`runIfNewReceiver`, `peerconnection.go:1760`;
`configureRTPReceivers`). An answer with two media sections that carry the same
mid, each one honest-looking (one SSRC, distinct from the other), passes the
new rule and still drives the library onto the same unrecovered path.

Reproduced against the fix: an answer whose second audio section is relabelled
with the first section's mid and given one SSRC of its own is accepted
(`err=<nil>`) and is followed by the same `rtpreceiver.go:544` panic. It
reproduces whether the duplicated section keeps its negotiated direction or is
forced to `sendrecv`.

Suggested fix: refuse an answer with a repeated mid. More robustly, vet that
the answer's media sections correspond one-to-one to the offer's (same mids,
no extra section) — this subsumes both blockers and the finding's whole
"Not examined" list rather than enumerating bad shapes. I added a repeated-mid
check to `vetAnswerSSRCs`, rebuilt, and both variants were then refused while
every honest and benign case still behaved as before.

## Confirmations (all positive)

- **Reproduces on main, refused on the fix.** The finding's recorded repro
  ends the test binary with the nil-pointer dereference on `f58bc3fc6`; on the
  fix the same answer is refused (`errAnswerSSRCs`) and the suite is `ok`.
- **Revert check.** Removing the `vetAnswerSSRCs` call from
  `vetAnswerCandidates` makes `TestAnAnswerWithASecondStreamInASectionIsRefused`
  fail (the second stream is accepted); restoring it passes. The new unit
  matrix `TestAnAnswerNamesOneStreamPerMediaSection` passes. The recorded tests
  run as ordinary tests (no build tag, no env gate).
- **Honest clients.** A Pion loopback client's own answer (audio publish)
  connects through the fix; the full `internal/sfu` suite with `-race` is green
  (94 s), as is `internal/ws` (16 s). The rule refuses only what the library
  would over-read.
- **Library read surface.** `trackDetailsFromSDP` reads only `a=ssrc` and
  `a=ssrc-group` to count streams; it never reads **session-level** `a=ssrc`
  (it iterates `media.Attributes` only) — I confirmed a session-level `a=ssrc`
  is accepted and harmless, and the fix likewise ignores it, so the two agree.
  `a=rid`/`a=simulcast` go down the RID path (`receiveForRid`), which does not
  open a per-SSRC receiver the way the crash needs — I confirmed a section with
  extra `a=rid`/`a=simulcast` lines is accepted and harmless. So the rule not
  looking at rid/simulcast/session-ssrc is safe.
- **`ssrc-group:SIM` refusal is safe.** The SFU offers each layer as its own
  m-section (see `web/src/talk/composables/webrtc/sdp.ts`), so a browser is
  never asked to simulcast within one section and will not answer with a SIM
  group; refusing SIM rejects nothing honest.
- **Interplay with H-L8-07.** `p.rtcp.declare(answer.SDP)` runs only after
  `SetRemoteDescription` returns nil (`room_signal.go:31`); a refused answer
  returns earlier, so `declare` never sees a rejected answer. `declare`'s own
  SSRC parse (`ingress.go`) is an independent per-line single-space `Cut` with
  its own budget and does not conflict with the new vetting.
- **Refusal path cost.** A refused answer returns an error; `internal/ws`
  logs it at warn and the offer watchdog resends (`room_signal.go`), capped at
  `maxOfferResends = 6` before the peer is dropped. Answers are metered by the
  `maxSignalingPerSec = 200` budget and the 64 KiB frame cap. No goroutine or
  timer is pinned per refused attempt; `SetAnswer` on a refused answer touches
  no connection state. The warn log is not itself rate-limited, but the resend
  cap and the per-second signaling budget bound the volume.

### How the library and the vetting read each attribute

The library counts streams in `trackDetailsFromSDP` (`sdp.go:79`, webrtc
v4.2.26), section by section, and then attaches them to transceivers by mid.
Each thing it reads there, compared with the vetting:

| What the library reads | How | Vetting |
|---|---|---|
| Section direction (`getPeerDirection`, media then session level): skips recvonly and inactive sections | attribute key | More strict: it vets every section, whatever its direction. |
| `a=mid` (`getMidValue`): skips sections without one; receivers are keyed by it | first `mid` attribute | More strict: the first `mid` (pion/sdp `Attribute`, the same choice) must equal the offer's mid at the same position, and the count must match. Repeated, missing or foreign mids are refused. |
| Media kind: skips kinds it does not know | `m=` line | More strict: it vets every section. |
| `a=ssrc-group` FID and FEC-FR: demote the repair SSRC | split at single spaces, exactly three parts, base-10 numbers; anything else is ignored | Same reading where it accepts: the same split, three parts, and only canonical decimal numbers (`parseSSRC` round trip), so both get the same two numbers. More strict otherwise: any other group (SIM, other separators, extra parts, signs, leading zeros, a self-repair, circles, two primaries) refuses the answer, where the library would ignore the line. |
| `a=ssrc`: one track per distinct SSRC that is not a repair | first token before the first space, base 10; a line that does not parse is ignored | Same reading where it accepts: the same first token, required to be a canonical decimal, so it is the same number. Distinct SSRCs are counted as a set, the same dedupe as the library. More strict otherwise: a line the library would skip, or would read as another number, refuses the answer. |
| `a=msid` and the `msid:` part of an `a=ssrc` line | labels (stream id, track id) | Not read. Harmless: they never change how many tracks a section has. Their only other use is the RID condition below. |
| `a=rid` / `a=simulcast` (`getRids`) | with an msid, they replace the section's tracks with one RID-based track | Not read. Harmless: this path ends with one track, and RID encodings get no per-SSRC receiver (`startReceive` skips them, `startReceiver` returns for RID tracks). Tested earlier: accepted and harmless. |
| Session-level `a=ssrc` | never read (only media attributes are) | Not read either. Same result. Tested earlier: harmless. |

Attribute keys are compared exactly on both sides (`ssrc`, `ssrc-group`,
`mid`). A key in other capitals, or with a stray character in it, is ignored
by both.

**Re-parse.** The library reads the vetted SDP after it has been marshalled
and parsed again. I checked that this round trip cannot change how many
streams the library counts:

- A value without a bare carriage return comes back unchanged. That includes
  spaces and tabs, which is why the spacing variants reached the library intact
  in round 1.
- A bare carriage return inside a line makes pion/sdp trim the end of the value
  when it parses the line again.
- The round trip never adds an attribute, and never turns a key into `ssrc`.
- Every value the vetting accepts as an SSRC id or a group is free of that
  character, so it comes back unchanged.

So the difference only touches values the vetting already refuses. This is an
oddity of the pion/sdp parser worth reporting upstream (NOTE), but it is not a
gap in the vetting.

**Across answers.** The rules are checked per answer. Across answers, the
library starts a section's receiver only once (`haveReceived`), and a section
whose SSRCs change is stopped and replaced by the library itself. I found no
way, across a sequence of answers that each pass, to put two streams on one
receiver. I worked this out by reading the code and tested it with the
renegotiation case below. A receiver whose start failed on an SRTP error was
not examined (NOTE).

### PendingLocalDescription on every path

- **First negotiation:** checked against the first offer (tests above).
- **Renegotiation:** a second member publishes, the SFU sends the first member
  a new offer, and a mutated answer to it is refused. The honest answer is then
  applied, the connection is `connected` and signaling is `stable`. Tested.
- **Late answer after the watchdog resent the offer:** with a short
  `offerTimeout`, the first answer arrives after the resend and is accepted. It
  is the same pending description, because the watchdog resends it and the SFU
  creates offers only in the stable state (`room_signal.go:113`). Tested.
- **ICE restart and rollback:** the SFU does neither.
- NOTE: an answer to an older offer N, sent while offer N+1 is pending, is
  compared with N+1. When the sections and mids agree (the SFU reuses
  sections), it passes and Pion applies it, which uses up offer N+1. The
  client's real answer to N+1 then fails with a signaling-state error, and the
  next round of signaling repairs that. This happened the same way before the
  fix, and the SSRC rule still applies to such an answer. It is not a
  regression and not a crash.
