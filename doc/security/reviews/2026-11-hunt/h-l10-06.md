## What the fix does

`eraseInTransaction` (internal/auth/account/account_delete.go:95-124) runs the erasure transaction again when it fails with SQLSTATE 40P01 (`db.IsDeadlock`, internal/db/errors.go:16-22):
- at most `eraseAttempts` = 3 attempts;
- a pause of 20 to 100 ms between them (`20 + rand.IntN(80)`), ended early if the request ends;
- after the third deadlock, `auth.ErrServerBusy`: 503 UNAVAILABLE, "the server is busy, try again shortly".

`ConfirmIdentity` stays before the loop. The 503 is added to the swagger annotation and to api/openapi.json.

## (1) Is a rerun safe? I read the whole path myself

Everything up to the commit happens inside the one `pgx.BeginFunc` transaction:
- **eraseWith** (account_erase.go:83-102): `SELECT ... FOR UPDATE` on users, `pinnedOf`, `runErase` over the merged steps, then the anonymise UPDATE. All of it runs on `tx`.
- **The steps of every domain:** the registrars are internal/auth/account, chat/account, communityevents/accountdata, emoji, wiki, push, bot, later, discordimport and webhook. A `userdata.Step` is `{Order, SQL, Arg, Keys}` (internal/userdata/userdata.go:58-63): SQL only, no Go callback. `execErase` runs every step on `tx`.
- **Session settings:**
  - `mnema.audit_scrub` is set with `set_config(..., true)`, which is local to the transaction;
  - none of the steps uses an advisory lock, NOTIFY or dblink (grep over every file that holds steps and over migrations 0103 and 0104);
  - the statement timeout (`db.WithStatementTimeout`) is a context value that the pool applies to the connection on acquire, so it is the same for every attempt.
- **The audit entry:** `Audit.RecordTx` (internal/audit/audit.go:78-100) is one INSERT on `tx`. It reads the actor and request id from `ctx` and has no side effect.
- **Triggers inside the transaction, which roll back with it:** the guards of migration 0103 (`erased_person_guard`, `erased_message_stays_empty`, `users_deleted_is_final`, `audit_log_erased_person`, `message_report_erased_people`), the message counters, and the migration 0104 column (not touched by the erasure).
- **After the commit only** (deleteAccount, lines 67-79, reached only when `err == nil`): `removeObjects` (object store), `announceUnpins` (pins_changed events), `endDeletedAccount` (voice kick, disconnect, `OnAccountEnded`, the user_disabled broadcast) and `Sessions.End` (cookie). No mail is sent on erasure.

A deadlocked attempt therefore leaves no trace outside the database. Each attempt collects `keys` and `unpins` again from the current rows, into a new `gone` variable inside the loop. One sequence value may be consumed by a rolled-back attempt (the audit_log id); that is harmless.

## (2) Does each retry start from a clean state?

- `pgx.BeginFunc` rolls the transaction back when the function returns an error. The next loop iteration calls `BeginFunc` again, which acquires a connection and begins a new transaction. No statement and no transaction object is reused.
- The deadlock error surfaces through `fmt.Errorf("erase %q: %w", ...)` or directly from `CollectRows`, and `errors.As` finds the PgError through the wrapping.
- An attempt that finds the account already erased by a parallel request gets `pgx.ErrNoRows` from the first SELECT. That is not a deadlock, so it is returned, and deleteAccount answers 204 as before.

## (3) The password and 2FA check

`ConfirmIdentity` runs once before the loop and is never repeated, so a code cannot be replayed through the loop and a lockout is counted once. The loop cannot be entered without a successful confirmation.

NOTE (existed before, unchanged): the factor check spends the TOTP step (`UPDATE user_totp SET last_step = $2 WHERE ... last_step < $2`, internal/auth/two_factor_store.go:206) or the recovery code in its own commit, before the erasure. After a 503, the web form keeps what was typed. A member who submits again within the same 30-second step with the same code gets a refusal that counts as a failed code. The same was true after the old 500. The message "try again shortly" invites an immediate retry, though. Asking for a new code in the 503 case, or not spending the step until the erasure commits, would be a follow-up; it is not needed for this fix.

## (4) The bound, cancellation, the 503 and the client

**Bound:** three attempts. Two pauses of 20-100 ms. Each attempt is bounded by the bulk statement timeout per statement.

**Cancelled mid-loop:**
- A cancel during the pause returns `ctx.Err()`.
- A cancel during an attempt makes its statements fail with a context error, which is not 40P01, so the loop returns it.

In both cases `err != nil`, so none of the after-commit steps run and nothing was committed. I checked this by reading only; there is no test for it.

**503:**
- The sentence is in the error catalogue golden file (internal/repo/testdata/error_messages.golden.json), and the internal/repo test passes.
- `make openapi-check`: exit 0.
- `make openapi-diff`: "no breaking changes since v3.0.10", exit 0. The 503 is an added response; doc/api-stability.md covers status codes through the OpenAPI document.

**Web client:**
- The delete form (web/src/settings/components/AccountData.vue:59-86) catches the error and shows `caughtErrorMessage`, which maps the sentence to `errors.serverBusy`: en "The server is busy. Try again in a moment.", de "Der Server ist ausgelastet. Versuche es gleich noch einmal."
- `resetLocalSession` runs only after a successful erasure.
- The bound test confirms that `/api/auth/me` still answers 200 afterwards.
- A 503 UNAVAILABLE also fires the client's `onUnavailable` listener. That listener refreshes the server feature list, at most every few seconds (web/src/stores/serverFeatures.ts:68-76). This is harmless.

**My constructed deadlock from the H-L10-05 review** (the erased member had timed out the reporter): unchanged. Both orders still abort the **report** (40P01, the reporter gets 500). The erasure answers 204, the account is erased, and nothing of her text is left. That cycle is closed by the report's insert, so the erasure is not the victim and the new loop is not involved.

In the opposite timing, with the report waiting more than a second before the erasure reaches `timeout_by`, the erasure would become the victim. That is the same mechanism as this finding, and the new loop now retries it. So the statement "the erasure always wins" in my H-L10-05 round 2 needs that qualification; see the document list below.
