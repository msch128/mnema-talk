FINDINGS

1. should-fix — web/src/lib/media/group.ts:190-194 (isCommitForUpdatedEpoch), SECURITY.md:732-739
   The rule stops the committer going back, but not the others, so one honest-relay ordering now splits where the old code converged.
   Ordering (server order, 3 members A<B<C, B leaves the Talk): C's renewal, B's renewal, A's removal of B (A built it on C's renewal before B's reached it).
   - A: takes C's renewal, removes B, ignores B's late renewal -> epoch 4 {A,C}.
   - C: own renewal, goes back to B's (lower id wins), then A's removal does not verify -> stays at epoch 3 {A,B,C}, a group that still holds B's leaf and a key B has.
   Measured (scratch test, fake clock): PR: "alice 4 {1,3}" vs "carol 3 {1,2,3}", split; carol only starts over at Alice's NEXT commit (keys none, re-offer). Base 00289dc3f, same ordering: Alice goes back, her following sync removes Bob again on Bob's branch, Carol takes it, both end at 4 {1,3}, nobody restarts.
   Repair in production is the existing start-over: 5 s of newer-epoch frames from the committer (callEngine.ts:140-153) or the committer's next commit. If A publishes no media, the next commit can be 20 minutes away (A removes C as silent: C's heartbeats name another epoch), and until then A cannot open what C seals.
   So the "removed member comes back" problem moved from the committer to the members that took the lower renewal first, and lasts longer there than it did before.
   Suggested fix (either): (i) the committer's commit decides the branch: a member that went back to the lower renewal keeps the state it left until CONFLICT_MS and returns to it when the committer's commit for that epoch verifies against it; or (ii) cheaper: when the committer ignores a rival renewal only because a commit followed (it verifies against saved.state and would have won), it commits once more at once, so members on the rival branch see a commit ahead and start over immediately instead of waiting. Add the ordering above as a test either way.
   SECURITY.md:737-739: the new sentence is accurate for the member it describes, but "so the call does not split" two lines above now has this exception; say that such a split is left to the start-over.

3. should-fix — web/src/lib/media/groupSimChecks.fixture.ts:153-156 (keyPackage) with groupSync.ts:156-164
   The checker marks a member "restarting" for ANY key package from someone in the receiver's tree; the product does so only for a package that differs from the leaf and is new (group.ts:132-133). With repair 2 a lone lowest id repeats the same package every tick (2 s in SIM_TIMING), so for every member whose tree still lists it the check "a lower live id commits now" (checkSender :209-216) is switched off until the next epoch, again and again. A non-empty commit from the wrong member would pass unseen in exactly the stale-tree runs this PR touches. Code reading, not run. Fix: mirror the product: only a package whose signature key differs from the leaf the receiver holds.

4. note — web/src/lib/media/group.ts:192
   The rule is "current epoch === saved epoch + 1", not "the renewal is the last commit". They differ in one corner: a non-rival welcome onto a group of one (joinFromWelcome, group.ts:164-168) replaces the state without dropping selfUpdate, so a welcome into another group that happens to be at saved+1 leaves the rollback armed for the rest of the 10 s. Strictly narrower than before (the old code had no epoch condition at all), so not a regression. Cleaner: drop selfUpdate whenever a commit other than the renewal, or a welcome, is adopted. That also wipes the pre-renewal epoch's secrets at once instead of up to 10 s after a removal (groupBase.ts:221-224 keeps them alive).

5. note, predates the PR — group.ts:140-169, groupSync.ts:240-242
   A member keeps its key package (and init key) after joining, and a group of one announces that same package. An old welcome built on it can be replayed to it later. Tested on base and PR alike: Alice is welcomed by Bob into {A,B,C}, both leave, Alice is alone at epoch 3, Bob is listed again and the old welcome arrives under his id: Alice takes it and is back at epoch 2 {1,2,3} (a key the departed Carol held), and her next sync removes Carol but keeps Bob's old leaf (3 {1,2}), without a fresh package from Bob.
   Needs the server, or a member who was in that old tree and is the lowest of it still listed; both can already steer a member under the documented caveat, so I rate it low and did not escalate. Repair 2 does not widen it: the tick sends the package every present member already has, and welcome acceptance is unchanged. Fix belongs in a PR of its own: wipe the init key after a successful join and re-found before announcing.

ANSWERS

Q1 clean, with finding 5 as context.
- (c) only adds a conjunct to isCommitForUpdatedEpoch, so it accepts a subset of what the old code accepted; nothing is taken that was refused.
- (a) Each re-announcement is the SAME package (this.own; the new unit test asserts identical wires). A fresh one is not possible without re-founding, since the group of one's own leaf uses those keys. Reuse costs repair, not safety: a member that already holds the sender's leaf with that key ignores it (group.ts:132), so a stale tree is not healed (the PR's remaining 4/2 seeds). Receivers act on it at most once (seen/same), commit vetting is unchanged (the package was already in `relayed`), and a third party gains nothing: every present member already had the package from the per-room announcement, and the welcome rules for a group of one are untouched. A lower id could already make a group of one step aside through any roster sync.
- (b) During the 1.5 s the newcomer takes a welcome from a higher id, where the old code had founded and added everyone in the same sync. That window already existed from the newcomer's offer until everyone had offered, and it is the documented "whichever member lets it in" caveat.
- No path hands out a media key of an epoch the reader is not in.

Q2 The rule is correct at the member that applies it; see finding 1 for what it leaves open. Orderings (A committer, B<C<D):
- B and C renew, nothing follows: lower id wins, loser goes back. Works (existing test, and the scripted RENEWAL_RACE).
- renewal vs committer's commit for the same epoch: committer's wins. Works (existing test).
- renewal, removal, late rival renewal at the committer: ignored, removed member stays out (new test; fails on base).
- same, at a member that took the lower renewal first: split, finding 1.
- renewal, add, late rival renewal: ignored now; members on the rival branch miss the add and start over. Base was no better: the committer went back and the newcomer sat alone in a branch nobody held.
- rival renewal after a further renewal: unchanged, the saved state is replaced by adoptUpdate, the late one fails to verify and is ignored.
- three renewals for one epoch: unchanged, a member that already switched once cannot switch again (selfUpdate is cleared), repaired by start-over.
