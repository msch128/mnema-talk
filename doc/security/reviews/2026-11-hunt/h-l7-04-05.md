## (1) The availability trade: a failed entry now fails the change

- **Intent.** SECURITY.md:281 ("every change is audited") and doc/moderation.md ("An append-only record
  of what was done") ask for the change and its entry together. The new section "When an entry can be
  missing" states it: "a failed entry fails the change". Failing closed is the documented intent.
- **Can an ordinary action now fail because of the audit insert?** I checked every cause I could find:
  - The immutability trigger (migrations 0027, 0043) fires on UPDATE only. The new INSERTs are
    untouched, also inside the account erasure's `mnema.audit_scrub` transaction: the
    `auth.account_delete` entry is inserted after the scrub, in the same transaction, and carries no
    name.
  - Size. SanitizeDetails never fails (audit/sanitize.go:44-65): lists are halved, then
    request/after/before/params are dropped, then the result is `{"truncated": true}`. Content is cut
    at MaxContentRunes = 4000 runes, and clip cuts by runes (textcut.Runes), so no invalid UTF-8 can
    reach PostgreSQL.
  - NUL bytes cannot occur: message text is TEXT, which already rejects them, and JSON keeps `\u0000`
    escaped as text.
  - `action` is checked to 1-64 characters, and all actions are constants. `actor_id` is nullable;
    RecordTx fills it from `Log.Actor` when it can.
  - A nil `*audit.Log` returns nil in RecordTx (audit.go:78-81), so the dropped `h.Audit == nil`
    checks are safe.
- **Probe with large and odd inputs** (through the real routes):
  - a 3999-rune message of ZWJ emoji sequences, edited 60 times, alternating with text that holds
    U+202E, stacked combining marks, an invalid UTF-8 byte sequence, a literal `\u0000` and 100 tag
    characters;
  - 30 replies, then a moderator delete with a 200-emoji reason;
  - a message of a member who then erased the account: edited before the erasure, deleted by the
    Owner after it;
  - a report with the odd text as its note.

  Result: every edit 200 and every delete 204. 60 `message.edit` entries, 1 `message.delete`. The
  erased member's message was deleted with 204.
- **Remaining exposure** (NOTE N1): the delete snapshot now goes through `GetMessage` (about 8
  statements: attachments, reactions, mentions, polls, forum, tags) under the row lock. If one of them
  failed deterministically for one message (a scan bug on a legacy row, say), that message could no
  longer be deleted with the normal route, where before the delete went through without detail. The
  mitigation already exists: bulk delete (moderation.go) still writes its entries after the commit and
  does not read this snapshot first. I found no such failing input.

## (2) Longer transactions

What moved into a transaction:

- delete: the snapshot (GetMessage, channel name, reply ids, edit versions), read after the row lock
  and the permission check, before the DELETE;
- edit: the snapshot, the last message_edits row and the read of the stored message;
- post and forum post: the read of the stored message (it was already loaded in the transaction when
  the channel had webhooks);
- reaction: ReactionSummary;
- conversation start: ListDMs;
- event comment: the comment read;
- RSVP: Store.Get (event, counts, signups);
- webhook create: `get`;
- wiki create: getPage;
- register, report, event create, account delete: one INSERT into audit_log each.

There is no network or object-store call in any of these: all are SQL on the same transaction, and
the object deletes (`core.DeleteObjects`) and every publish stay after the commit. Locks: the message
row (FOR UPDATE for delete, FOR NO KEY UPDATE for edit and reaction) is now held for those extra reads,
a few milliseconds at most. Registration holds the signup lock for one more INSERT.

## Round 2: ecb083716 "fix: an audit entry written after the commit does not end with the request"

The delta is on top of dc8adbe77. It answers S1 and S2 from round 1. Read in full: internal/audit/audit.go,
internal/audit/middleware.go, internal/audit/fake_test.go and doc/moderation.md.

**Verdict H-L7-04: MERGE.** S1 and S2 are resolved; one NOTE (R2-N1) is left for a follow-up.

### What changed

`afterCommit(ctx)` is `context.WithTimeout(context.WithoutCancel(ctx), 5*time.Second)`. RecordOrLog
writes through it. The admin middleware builds one such context after the handler and uses it for the
"after" snapshot (`finalizeEntry`) and for the entry. The documentation names "removing a member from
one Talk" (S1) and says a disconnect no longer loses the entry; what is left is a crash or a database
failure (S2).

### Checks

- **No cancelled context left on the write path.** Inside RecordOrLog everything uses the detached
  context:
  - `Record` → `RecordTx` → `l.Actor(ctx)`, which is `auditActor` and reads context values only
    (internal/server/hooks.go:23);
  - the pool acquire and the INSERT (`q.Exec(ctx, ...)` on the pool).

  In the middleware, the after-snapshot (`addStateChange`/`addCreatedState` → `Snapshot(ctx, l.DB,
  ...)`) now gets the detached context too. The before-snapshot still uses the request context, which
  is correct: it runs before the change. A cancellation there means the handler most likely fails as
  well, and then no entry is due.
- **Pile-up under a slow database.** The write runs synchronously in the caller's goroutine. No
  goroutine is started, so the number of writes at once is bounded by the requests in flight (plus
  the few background callers), and each waits at most 5 s, the pool acquire included. Before, a
  disconnected request ended at once. Now its goroutine lives up to 5 s longer, and only when the
  database is slow. The background callers that passed `context.Background()` (automod/hits.go:128,
  raid.go:45) had no bound at all before and now have 5 s, which is an improvement. The middleware's
  nested afterCommit inside RecordOrLog takes the earlier deadline, so the whole after-handler work
  stays within 5 s.
- **Shutdown.** These writes are not background jobs, so Drain need not track them. They run inside
  the handler, and http.Server.Shutdown waits for handlers for 15 s, longer than the 5 s cap. Only a
  handler that already outlived the 15 s (H-L7-08's case) can still write when main's defers run
  `pool.Close()`. Then either the pgxpool acquire on the closed pool fails at once (logged as "audit
  log write failed"), or a write already holding a connection delays pool.Close by at most the 5 s
  cap. Nothing hangs and nothing panics.
- **The test fails without the change.** With audit.go and middleware.go from dc8adbe77 and the new
  test kept: `fake_test.go:109: RecordOrLog with a cancelled request context wrote 0 entries, want 1`,
  FAIL. With ecb083716: PASS.
- **A real pool, once.** In a reviewer-only integration probe (not committed), RecordOrLog with an
  already-cancelled context against the real PostgreSQL pool wrote 1 entry on ecb083716 and 0 entries
  with the dc8adbe77 audit code.
- **Gates.** All exit 0 or ok:
  - `go vet` (internal/audit; with `-tags=integration` internal/audit and internal/server), gofmt;
  - unit tests of internal/audit and internal/repo;
  - scripts/complexity-check.sh, `make docs-check`, scripts/check-english-only.mjs;
  - `go test -tags=integration -run Audit` over internal/server, internal/audit and internal/chat/...

### Note

- **R2-N1 (NOTE, follow-up).** The new sentence in the documentation, "a client that disconnects in
  that moment still leaves its entry", is true of the write itself. It is not true of handlers that do
  a post-commit read on the request context first and skip the entry when that read fails. Example:
  internal/chat/talks/talks_handler.go:89-105 (Talk settings, `channel.update`). After EditChannel has
  committed, `FillTalkFields(r.Context())` returning an error leaves the handler before the entry, and
  so does `IsDMTalk(r.Context())` ("talk update not audited"). A disconnect there still loses the entry,
  and the client is answered 500 for a committed change (the H-L7-05 shape). Other sites only lose
  detail on such a failure, which I checked at poll.go auditEnd and users_admin_talk.go:105: they
  still write the entry. Low moderation value. A follow-up should either move that read before the
  commit or use afterCommit for it, or the documentation should say "the write itself". Not blocking.
