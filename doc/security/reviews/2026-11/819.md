## 1. Root cause: confirmed

- `sendSocketEvent` (stores/socket.ts:241-245) sends only when `ws && isConnected`. Otherwise the event is dropped without any error.
- `rejoinAfterReconnect` runs only from `watch(reconnectCount)` (App.vue:197). `reconnectCount` is bumped only when `hadConnection` is already set (socket.ts:171), so it never fires on the first open.
- `resumeVoiceSession` (App.vue:202-206) runs on the first connect, but it returns early when `voice.currentChannelId` is already set (session.ts:306). An early manual join sets that.
- Result: a `voice_join` sent before the first open is lost, and nothing sends it again. The server never offers. The root cause is real.

## 2. Races

- **Ordering against the reconnect resume: correct.** `handleSocketOpen` sets `isConnected = true` (socket.ts:163) and then bumps `reconnectCount` (171). That queues two pre-flush jobs: the `socketUp` watcher and App's rejoin watcher. Both run in the same synchronous `flushJobs` pass. `resolve()` only queues the `await` continuation as a microtask, so `rejoinAfterReconnect` still sees `joinAwaitsSocket === true` and backs off. I checked this with a probe that wires a real `watch` the way App.vue does: exactly one `voice_join` (non-resume) is sent. The PR's own test calls `rejoinAfterReconnect()` before flipping the socket, which is not the real order, but the outcome is the same.
- **Leave while waiting:** `endCall` bumps `joinGeneration`. On wake the join sees the mismatch and returns, and the flag is cleared. The `voice_leave` is dropped while the socket is down, which is harmless because the server never saw a join. Media and roster cleanup happen in `endCall`. But see FIX 1: the held stream is not stopped in every pipeline variant.
- **Joining another channel while waiting:** both joins wait. On connect, A's continuation runs first (gen mismatch, so it clears the flag and returns), then B sends. No rejoin can run between the two continuations. Only one join is sent. Fine.
- **Several joins of the same channel while waiting:** `canJoinVoiceChannel` lets a second click through, because `localAudioStream` is still null while waiting. That second join tears down A's pipeline and asks for the mic again. The older join backs out. The cost is a second getUserMedia, and nothing is wrong on the wire. The mic-wait phase already behaves this way, so I make no change request.
- **Socket never connects:** no timeout. The join promise and its watcher stay pending until the next `isConnected` true edge. A leave bumps the generation, so the eventual wake is a no-op. The leak is one watcher closure per abandoned join, which is bounded and acceptable. While waiting, the UI shows the Talk as joined (`voice.setChannel` makes `voice.isConnected` true), which is also true during the mic wait. The connection banner already explains why. Acceptable.
- **Reconnect while waiting (the socket was up before, then dropped, then the member joins):** the resume is suppressed and the held join sends a fresh `voice_join`. That is correct, because the server needs a join for the new channel.
- **Logout while waiting:** `endAccountSession` calls `leaveVoiceChannel` (gen++). `closeSocket` resets `hadConnection`. On the next login's open, the stale watcher fires, sees the mismatch and clears the flag. No `reconnectCount` bump happens for that open, so nothing is suppressed. Fine.
- **Unmount:** the RTC state lives in the composable's shared cx, and `watch` is created after several `await`s, so it has no active effect scope. An unmount cannot stop the watcher and strand the flag. Fine.

## 3. Can the flag get stuck?

It is cleared on both exits after the wait. It can stay up in one case: if `setupPeerConnection` throws between the wait and line 173. `new RTCPeerConnection(rtcConfig)` at peer.ts:150 throws on an invalid ICE server entry or under a browser policy. The exception rejects the join, `st.joinAwaitsSocket` stays `true` for the page's lifetime, and every later `rejoinAfterReconnect` returns early. After that, any socket drop in a later call loses that call's media for good. This is an edge case, but the fix costs nothing (FIX 2).

## 4. Other events that `sendSocketEvent` drops the same way (not for this PR)

- `voice_join` of a lobby (lobby.ts:54). Dropped before the first connect. It has `LOBBY_WAIT_MS` with a "lobby unavailable" toast, so it fails visibly rather than hanging. This is the closest sibling of this bug and the strongest follow-up candidate.
- `voice_join` resume (session.ts:216). Pre-existing related issue, confirmed by a probe: a reconnect while the join is still in its microphone wait (prompt open) sends `voice_join {resume:true}` for a join that was never sent, and then the real join follows, so two joins go out. The new flag covers only the socket wait. Setting it from `voice.setChannel` until the send would cover both.
- `voice_leave` (session.ts:250). A leave while the socket is down is lost. The server holds the seat until its grace time runs out, so others see a ghost member for a short while.
- `webrtc_answer` / `webrtc_candidate` (peer.ts): lost during a drop, then recovered by the resume renegotiating.
- `media_handshake` (mediaRoom.ts:18): held until `openMediaRoom`. Wires sent during a drop are lost, then recovered by `mediaCall().resume()`.
- `voice_mute_state`, `webrtc_subscribe`: re-sent by `attachSubscriptions` on rejoin. Covered.
- `stage_hand` / `stage_talk_power` (useStage.ts), `talk_reaction`, `webrtc_screenshare_start/stop`, `webrtc_camera_stop`, `webrtc_layers`, `webrtc_request_keyframe`: user actions during a drop are lost silently, with no retry and no notice. Screenshare and camera start/stop state is not re-announced by the resume path, which deserves a separate check. `typing`, `voice_speaking` and `webrtc_diag` are ephemeral and fine to drop.

## Findings needing a change

**FIX 1: microphone left open when a held join backs out.** web/src/talk/composables/webrtc/session.ts:164-167.
`prepareAudioPipeline` stops its streams on a generation mismatch (session.ts:81-89). The new back-out after the socket wait does not. In the normal pipeline the raw capture is in `st.rawMicStream`, and `endCall` → `teardownMicPipeline` stops it. But there are paths where the capture is sent unrouted and never stored in `st`:
- no AudioContext: micPipeline.ts:321-323 returns `stream` directly;
- `routeCapture` failing, or `contextStalled` with 100 % volume and no filter: micPipeline.ts:340.
In those paths nobody stops the stream.

Failure scenario: the member picks a Talk right after load, in a browser where `new AudioContext()` throws (WebView or policy). They grant the mic while the socket is still connecting, then click Leave. When the socket comes up, the join returns at line 166 without stopping the tracks. The microphone stays captured, and the OS and browser recording indicator stays on until a reload.

The same leak happens when they join another Talk while waiting, because `cleanupVoiceAudio` does not know the held stream. I reproduced this with a probe (`window.AudioContext` throwing, leave while held, then `stream.getTracks()[0].stop` was never called). The default-pipeline variant of the same probe passes. Before this PR the window between the mic grant and the send had no await, so the leak is new. It can also last a long time, because the reconnect backoff goes up to 30 s and the wait may never end.

Fix: `stopStreams(sendStream)` in the mismatch branch, matching `prepareAudioPipeline`. Add a unit test: leave while held, AudioContext unavailable, expect the capture's tracks to be stopped.

**FIX 2: the flag can stick if the post-wait code throws.** web/src/talk/composables/webrtc/session.ts:171-173.
`st.joinAwaitsSocket = false` runs only after `setupPeerConnection` and the send. If `new RTCPeerConnection(...)` throws (peer.ts:150, for example an invalid ICE server URL from the server's config), the flag stays `true`. Every later `rejoinAfterReconnect` in this page then returns early, so after any socket drop in a later call the media is never resumed and the call goes silent.

Fix: clear the flag right after the wait, unconditionally (`st.joinAwaitsSocket = false` directly after `await socketUp(cx)` / before the generation check). Nothing async can run between that point and the send, so the reconnect guard is unchanged. Alternatively use try/finally.

Optional, not blocking: follow up separately on the lobby `voice_join` (lobby.ts:54) and the resume during the mic wait (section 4).

VERDICT: FIX
1. web/src/talk/composables/webrtc/session.ts:164-167: stop `sendStream` when a join held for the socket backs out. Otherwise, without an AudioContext (or with unrouted capture), a leave or a switch while waiting leaves the microphone captured until a reload. Reproduced with a probe test.
2. web/src/talk/composables/webrtc/session.ts:171-173: clear `joinAwaitsSocket` right after the wait, not after `setupPeerConnection` and the send. A throwing `new RTCPeerConnection` otherwise leaves the flag up, and every later reconnect resume is suppressed for the page's lifetime.
