### Findings

**A-1 SHOULD-FIX: the PR gate and the release read the trailer block differently when the text contains a `---` line.** scripts/security-floor.sh:55 uses `git interpret-trailers --parse`, which stops at a `---` line (the patch divider). The release reads `%(trailers)` from the commit (lines 43 and 73), and that ignores the divider. I reproduced both directions:
- False negative: the PR body `Text\n\nSecurity-Floor: raise\n\n---\n\nNotes after a rule.\n` passes `--check-message` (rc 0). The same text as the commit message makes the release decision exit 1. So the gate lets through exactly the failure it exists to stop, and that release gets no signed bundle.
- False positive: the PR body `Text\r\n\r\n---\r\n\r\nMore\r\n\r\nSecurity-Floor: raise\r\n` is refused (rc 1), but as a commit it raises correctly (probe 16 gives 0.2.0). That blocks a valid security-fix PR.
- `---` lines are common here: 39 of the last 100 merged PR bodies have one.

Fix: `git interpret-trailers --parse --no-divider`. With that flag, both inputs above give the release's answer (I checked both). Also add both inputs to `test_check_message_mode`.

**A-2 SHOULD-FIX: `--check-commits` passes when the range cannot be read.** scripts/security-floor.sh:41 uses `for sha in $(git log --format=%H "$1")`, so a failing `git log` is ignored. `--check-commits 0123…4567..HEAD` (an unknown base) and `--check-commits nonsense` both print git's fatal error and exit **0**. In ci.yml:199 both SHAs are present today (`fetch-depth: 0`; head.sha is a parent of the merge ref, and base.sha is on the fetched base branch), so I know of no reachable case. Still, a gate in a protected area should fail closed. Fix: `shas=$(git log --format=%H "$1")` before the loop. Under `set -e` the assignment exits on failure.

**A-3 NOTE: typos in the marker are still dropped silently.** `Security-Floor: raise.` (a trailer whose value is "raise.") and `Security-floors: raise` both give `keep` with no error and no warning, in both the release and the PR gate. That is the same "meant but dropped" class as H-L11-01. `test_other_value_keeps` deliberately keeps `Security-Floor: lower` silent. My suggestion: refuse any line matching `^\s*security-floor\s*:` that is not a parsed trailer with the value `raise`, since there is no other legitimate value.

**A-4 NOTE: a checkout without tags fails closed only by accident.** In a repo without tags, `prev` is empty, so the check runs over the whole history and every raise maps to the version being released. In a throwaway repo (probe 27: `git clone --no-tags`) the script exited 0 and printed the release's own version, a silent over-raise. In this repository it fails, but only because c50b6886e is in the full range. The release checkout fetches tags, so this is not reachable today. Suggestion: refuse when `git describe` finds no `v*` tag below `<rev>` while `git tag --list 'v*'` is not empty, or refuse when no tag exists at all.

**A-5 NOTE: "the pipeline has no way to lower the floor"** (doc/desktop-trusted-client.md, new text) is true for the pipeline's own decisions. A maintainer who pushes a wrong lower `vX.Y.Z` tag on a newer commit lowers it (probe 24). That needs write access to tags, so it is a documentation nuance and not a defect.

**A-6 NOTE: a marker line quoted in a code block fails the release.** A commit that documents the marker on its own line (fenced or indented block) cannot be told apart from a misplaced marker, and that release gets no bundle. This fails loudly, and the PR gate catches it first when the merge body is the PR description. Acceptable, and worth one sentence in AGENTS.md item 11 ("quote it inline, never on its own line").

**A-7 NOTE: the PR gate only sees the description at the last push.** `pull_request` runs on the default types, so editing the description to add the trailer at merge time does not re-run the check. Also, the repository's squash default is `COMMIT_MESSAGES` (gh api), so the ci.yml:191-194 comment "(the squash message)" holds only because maintainers merge with the description as the body, which is current practice (#448 and c50b6886e). The release-time check is the backstop in both cases. A comment correction is enough.

**A-8 NOTE: shellcheck.** `shellcheck -s sh scripts/security-floor.sh` reports SC1087 (error severity, a false positive for `$marker[[:space:]]`) at lines 31-32. It is not a CI gate here, but other scripts in `scripts/` are kept clean with directives. Writing `${marker}` silences it.

**A-9 NOTE: other effects.**
- `RealHistory` and `DocumentedRaises` in test_security_floor.py need the full history with tags, so `make test-scripts` fails in a shallow or tagless local clone. The failure message says so, and CI uses `fetch-depth: 0`.
- Rebuilding v1.2.0 from its tag now fails (see run 1).
- doc/upgrade.md:865 (unchanged) still says "(the floor is a high-water mark)" in the 1.2.0 rollback note. It now reads better as "(the high-water mark)".

### Agreement probes

For each case I fed the PR check the body alone, as CI does (`printf '%s\n' "$PR_BODY" | sh … --check-message`). The release decision ran on a commit built the way GitHub stores a squash commit: title, blank line, body. I used `git commit-tree` in throwaway repos and ran everything with `dash`. 25 of 26 cases agree:
- **Merge-train bodies:** an override block (`BEGIN_COMMIT_OVERRIDE … END_COMMIT_OVERRIDE`) with the trailer as its own last paragraph, in LF and in CRLF, passes and raises. The trailer directly under `END_COMMIT_OVERRIDE` in the same paragraph is refused by both.
- **Other bodies that pass and raise in both:**
  - CRLF line endings, with or without `Co-authored-by`.
  - A `Signed-off-by` line, a prose line and the trailer in one paragraph (git's 25% rule applies to both readers the same way).
  - Trailing spaces, two trailers, a `# heading` line above the trailer, an HTML comment above it, `Release-As` followed by the trailer, and trailing blank lines.
- **Bodies both refuse:**
  - A `BREAKING CHANGE:` paragraph after the trailer.
  - Prose above the trailer in the same paragraph.
  - A wrapped prose line that starts with the key.
- **CR-only line endings:** both pass and neither raises. Removing CR joins the lines, so the marker disappears without an error. GitHub never stores CR-only messages, so this is a NOTE only.

**R2-1 SHOULD-FIX: the PR check refuses a valid body that is a single paragraph.** A PR description consisting only of the trailer block (`Security-Floor: raise`, or `Release-As: 3.0.10` followed by `Security-Floor: raise`) is refused by `--check-message`, because `interpret-trailers` reads the only paragraph as the subject. The squash commit has the PR title above it, so the release reads the trailer and raises the floor. This is the only disagreement I found. It blocks a correct security-fix PR, and it never lets a bad one through. It slipped past the agreement test because `test_release_and_pull_request_checks_agree` (test_security_floor.py:157-160) feeds `--check-message` the full message including `fix: x`, while CI feeds it only the body.

Fix: in ci.yml, pass the title through env and check `printf '%s\n\n%s\n' "$PR_TITLE" "$PR_BODY"`, or prepend a subject line inside `--check-message`. Then make the test feed the body alone, as CI does, and add the body-only case.

**R2-2 NOTE: the stricter line rule refuses prose and code-block quotes.** A line that starts with `Security-Floor`, including a wrapped, indented list item, now fails the commit. Run over the whole history, `--check-commits` flags c50b6886e (expected) and also 4c060836c (v0.7.25). Its body has the wrapped line `  Security-Floor: raise trailer signs its bundle with security_floor set`.
- That commit is long released, so the check never reads it again.
- The same wording in a future PR fails loudly, and the PR check catches it before main whenever the description is the merge body.
