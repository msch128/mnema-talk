## SHOULD-FIX

### S1. The grace timer's "end the presence again" branch is untested and its comment is inaccurate

`internal/ws/voice_presence.go:121-136` (`claimed`, `onPanic`).

- The comment says only a panic *before* the seat was removed makes `onPanic`
  end the presence again. The code cannot tell the two cases apart: once
  `claimed` is set, `onPanic` runs `end()` after any panic, including a panic
  in a listener after the seat is gone. That second `endPresence` is then a
  no-op (`wasIn` false), so it is harmless, but the comment describes
  something the code does not check.
- Evidence that the branch is untested: in a scratch copy I replaced
  `onPanic` by `safego.Abandon` and deleted the retry. `TestPanicInOneMembersGraceTimerLeavesTheHubConsistent`,
  `TestGraceTimerPanicStillTellsTheOthers` and the other new tests still
  passed. Both tests panic in `h.Presence`, which runs after the seat was
  removed, so the retry never matters in them.
- What a panic before removal could be is thin: inside the locked section only
  `seatedLocked` and map operations run. If one of them did panic
  deterministically, the retry panics the same way and, as documented, ends the
  process, so the branch adds little. Either test it with an injected panic in
  the `keep` function (a nil entry in `h.rooms[ch]` makes `seatedLocked`
  panic), or remove the branch and say in the comment that a panic after the
  removal is abandoned and one before it is not expected.
- Smaller consequence of the same code: a retry runs `endPresence` a second
  time. If the member left and a new grace for the same key started in the few
  microseconds between the two calls, the second call would end that newer seat
  early (`keep` only looks at connections, not at a newer grace). The window is
  negligible; it is mentioned so the retry is not mistaken for free.

### S2. The fail-closed clean-up is not isolated per member, and it does not remove a seat that has no connection and no grace

`internal/ws/voice_kick.go:191-217` (`disconnectForRecheck`).

- The seat loop is guarded per member (`ws_perm_enforce_seat`, `Abandon`), the
  disconnect loop is not: `for id := range users { h.DisconnectUser(id) }`
  runs unguarded. A panic in one member's `DisconnectUser` (`c.close()` ->
  `conn.Close()`) skips the disconnects of every member after them and the whole
  seat loop. On the HTTP path `safego.handle` re-panics (`panic(again)`) into
  net/http's recovery (`internal/httpx/middleware.go:61`), so the process
  continues with some members not re-checked. On timers the process exits.
  Same guard as for the seats would make the clean-up fail closed per member.
- `KickFromVoice` removes seats only through a connection that holds the seat
  or through a pending grace. A seat in `h.voice` that no connection and no
  grace stands for is listed by `disconnectForRecheck` (it reads `h.voice` and
  `h.grace`) and then not removed. I confirmed it with a scratch test: join a
  Talk, clear the connection's voice room and its `h.rooms` entry (the state a
  half-finished leave would leave), call `disconnectForRecheck(nil)`; the seat
  is still listed afterwards. `kickUserFromChannel` already has the missing
  step (`removePresenceUnlessPresent(user, ch, nil)` "make sure the seat is
  gone", `internal/ws/perms.go:361-362`). Calling `removePresence` for each
  seat that was found in `h.voice` closes it. The state needs an earlier
  half-done leave to exist, so this is defence in depth, not an observed bug.

### S3. `GET /api/health` now changes outcome during storage blips; the Docker health check is the main caller that sees it

`cmd/server/storage.go:100-122`, `Dockerfile:101-102`, `docker-compose.yml:187-192`.

- Before: after a healthy start `Ready()` returned nil for ever, so the
  container could not turn unhealthy because of storage. After: one HEAD
  that fails or exceeds 2 s makes `/api/health` answer 503 for the next
  10 s (the probe cache) plus up to 2 s (the handler cache). The image
  `HEALTHCHECK` and the compose health check both call `/api/health`
  (interval 30 s, retries 3), so storage that is down or slow for roughly
  60-90 s marks the `app` container `unhealthy`. Docker itself does not
  restart on that, but anything that watches health does (an auto-heal
  sidecar, an orchestrator, `scripts/backup-common.sh` `service_start`, which
  waits for `healthy`, and the self-update page that polls `/api/health`).
  `doc/deployment.md` says "Do not use `/api/health` as a liveness probe", yet
  the shipped `HEALTHCHECK` does exactly that. A short blip (one slow HEAD
  while SeaweedFS compacts or the NAS is busy) is reported as an outage and
  clears 10-12 s later; there is no hysteresis.
- Suggested fix, either or both: count a probe as failed only after two
  consecutive failures (or keep the last good answer for one TTL when the
  failure is a timeout), and add a sentence to `doc/deployment.md` and
  `doc/operations.md` that the image health check now turns `unhealthy` during
  a longer storage outage and that this is intended. I could not look at the
  NAS auto-deploy poller (not part of the repository), so whether it reads
  container health is not checked.
- Not a problem, checked: the worst case of one `/api/health` call is the
  database ping (2 s) plus the storage probe (2 s) = 4 s, under the 5 s Docker
  timeout, and `healthCheck.check` serialises callers on its own mutex, so a
  hung storage costs every waiting caller at most that long, after which they
  read the cached result. `Probe` uses `HeadBucket`, the same call
  `ensureBucket` must already have passed before the store exists
  (`internal/s3/s3.go:97`), so a store whose credentials forbid `HeadBucket`
  never gets the lazy store to the "healthy" state in the first place and
  cannot be reported down for ever by the probe. MinIO and SeaweedFS
  answer HEAD on a bucket.

### S4. Nothing guarantees that `*s3.Client` satisfies `prober`; a mismatch silently disables the new check

`cmd/server/storage.go:107-110` (`store.(prober)`; `if !ok { return nil }`).

If the method signature of `(*s3.Client).Probe` is ever changed, the assertion
fails at run time and `Ready` goes back to "never reports an outage" with no
test failing (the test uses its own fake). Add
`var _ prober = (*s3.Client)(nil)` in `cmd/server` (or a test that asserts it).

## NOTE

### N1. Blast radius of "everybody"

`PermissionsChanged(nil)` that panics disconnects every connection and ends
every seat. That is the fail-closed choice and is documented, and the panic is
logged only five times a minute per site, so it cannot flood the log. I found
no panic source a member can trigger on purpose. If one exists later, an
admin's role or overwrite change would be the trigger and the effect a
reconnect of the whole community each time the offending member is seated.
A per-member guard inside the enforcement loops (disconnect only the member
whose step panicked) would shrink this, at the price of more code in
`perms.go`. Not required now.

### N2. Documentation is slightly stronger than the code for the HTTP path

`doc/operations.md` says a panic in the clean-up after a recovered panic ends
the process. On a request it does not: the re-panic goes to net/http's
recovery and the request answers 500 while the process lives (the change is
already committed). With S2 fixed the two cases are closer; otherwise one
sentence ("on a request the request fails with 500") is accurate.

### N3. `h.pending` connections are not part of "everybody"

`disconnectForRecheck` collects users from `h.clients`, `h.voice` and
`h.grace`, not from `h.pending`. `DisconnectUser` does close pending
connections of a user it is given, but a user who has only a pending
connection is not in the list. The normal enforcement (`filterPermClients`)
has the same scope, so this is not a regression.

### N4. Voice time under a deterministic panic

If the panic in `flushVoiceTime` repeats (say, a corrupt entry), the seconds
are restored and the timer re-armed every `voiceTimeFlushEvery`: one counted
panic per interval for that member and no write, until the member's entry is
rewritten. No crash and no double count (the restore runs once; `written` is
set only after the write returned). Between the committed write and
`written = true` there is no code that can panic. In `endPresence`, a panic
inside the locked section after the three `delete`s and before the seat is
removed (`h.stage.forget`) would, on a retry, take the seat out without the
stay's voice time (`voiceSince` is gone). That is only reachable through the
double-panic case already documented.

### N5. Web: bounded noticing relies on failing requests and on socket reopen

`web/src/stores/serverFeatures.ts`, `web/src/shared/lib/api.ts:230`,
`web/src/stores/chat/socket.ts:36-39`.

- A healthy server is not polled: the store asks again only while something
  is reported down (every 30 s), when an `api()` request answers
  `503 UNAVAILABLE` (at most once per 5 s), and when the socket reopens. XHR
  uploads go through `api()` (`browserTransport` -> `xhrUpload`), so they are
  covered. Plain `fetch` and `<img>` loads of media that fail with 503 are not,
  so a member who only reads sees broken pictures and no notice until one of
  the three triggers happens. The outage is therefore noticed "when it matters
  (an upload fails)", not within a fixed time. This looks like the intended
  trade-off; it is stated here so the task's "bounded time" is read the same way.
- The health check cannot loop on itself: its own 503 is an accepted status,
  so it never reaches the `onUnavailable` handlers. A request that never
  answers is cut after 10 s (`AbortSignal.timeout`, already used elsewhere in
  the app, so no new browser requirement) and the timeout is handled like any
  failed check; during a known outage the 30 s timer is re-armed, otherwise the
  next call asks again.
- Listener replacement (`stopListening?.()`) is only relevant when a second
  Pinia instance creates the store (tests); in the running app there is one.
- The 30 s outage timer is not paused for a hidden tab; browsers throttle it,
  and it runs only while an outage is known.
- An older server (a 503 with the bare error) still confirms nothing, as before
  (covered by an existing test).

### NOTE

#### N7. `DisconnectUser` under `safego.Locked`: no new risk

Same lock (`h.mu` write lock), same scope, now released on a panic. The only
callers in the repository are HTTP handlers and timers (`internal/auth/...`)
and the hub's own `disconnectForRecheck`; none holds `h.mu` (it would have
deadlocked before as well). Lock order is unchanged: `h.mu` is not held while
`c.close()` runs. `shutdown` panicking inside the lock (the isolation test
forces it) is now recovered with the lock free.

#### N8. A member whose own disconnect panics keeps the connection

In that case `c.close()` of that member is skipped (the panic comes from
`shutdown`, before it). The seat is still ended by the seat loop, so the
member holds no Talk seat or media peer, and every right is re-read per
request or event; the open socket is therefore not a right the change took
away. The test asserts the others are closed and nobody has a seat; it does not
assert anything about the broken member's socket, which is the right scope.

#### N9. `kickUserFromChannel` for collected seats: no double end, no double event

A seat that is in `h.voice` and in `h.grace` is one key in the map, so it is
handled once. Inside `kickUserFromChannel`, `leaveVoiceLocked` already takes
the grace and ends the presence, so for a connected member the following
`takeGrace` is nil and the final `removePresenceUnlessPresent` is a no-op
(`wasIn` false): one voice leave, one `voice_kicked` per connection. A seat
that only has a grace is ended by `removePresence` once. A connection that
reconnects between the two loops is kicked as well (over-kicks, fail closed).
The reason sent is `missing_permission` even when the real cause was a
panic; the old sockets are already shut down and drop it, so only a very fast
reconnect could see it.

#### N10. The test seam `graceKeep`

Unexported field in package `ws`, so only code in that package can set it, and
nothing outside tests does (`grep`). It is read once per grace expiry (one nil
check per fired timer, not a hot path) and replaces the keep check as a whole,
so the test does not exercise `seatedLocked`; the earlier tests cover that
path. `-race` clean: the field is written before `unregister` creates the
timer.

#### N11. Hysteresis: behaviour to know

- Probes only run when somebody asks. The second probe of a blip happens at
  the next `/api/health` call after 3 s. With only the 30 s Docker check
  asking, an outage that began between two checks is reported on the second
  check, so up to about 60 s after it began, then three failed container
  checks (about 90 s) make the container unhealthy. That is the intended
  trade-off of S3 and is within what the docs now say ("about 10-15 s" holds
  when callers are frequent; with sparse callers it follows their interval).
- Storage that alternates fail, success, fail, success is never reported,
  because every success resets the counter. A half-working store is therefore
  seen as healthy; a hard outage is not affected.
- Worst case of one `/api/health` call is unchanged: at most one probe per
  call (2 s) plus the 2 s database ping, 4 s, under the 5 s Docker timeout;
  the probe mutex keeps concurrent callers from probing twice.

#### N12. Web helper split: behaviour unchanged

`healthAsker` keeps the same state (`pending`, `asking`, `recheck`) in a
closure and `notifyRefusal` picks the same handler set as the two former `if`
lines (rules refusal first; 503 `UNAVAILABLE` second; a refusal can only be
one of them). The existing outage, connection and API tests pass unchanged.
`eslint` on both files and `vue-tsc --noEmit` are clean. A new Pinia store
still registers the failure listener once and replaces the previous one.
