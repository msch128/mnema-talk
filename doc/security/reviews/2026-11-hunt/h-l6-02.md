# Fix review: H-L6-02 (branch msch128/fix-h-l6-02, commit 1d8e07010)

Reviewer: an independent agent that wrote neither the finding nor the fix (it did the phase 2
reproduction and refutation of H-L6-02). Read-only: nothing in the repository changed, nothing

Base: msch128/hunt-lane6 at d62d54ce2. Diff reviewed: d62d54ce2..1d8e07010 (12 files).

## Verdict: MERGE AFTER FIXES

The cause is removed for messages: `reply_to_id` and `parent_id` on posting, scheduling and
uploading now answer the same bytes for a hidden message and for an unknown id, and the timing
does not differ. The category variant is fixed for the probe's request only. When the request also
has an invalid field, the hidden and the missing category still answer different bytes, and their
timing differs clearly (B1, S1). Both have the same small fix. The api-stability bullet sits in the
wrong section (S2).

## Findings

### B1 BLOCKER: a hidden category still answers unlike a missing one when another field is invalid

`internal/chat/channels/handler_channels.go:110-116` checks the category's visibility before
`CreateChannelWithStage` checks the name, the type and the sort order
(`internal/chat/channels/channels.go:96-105`, `cleanChannelInputs` and `CheckSortOrder`). A
missing category is only noticed later, in `lockCategory` (`channels.go:80-92`), after those
checks. So a request with an invalid name or type gets "category not found" for a hidden category
and the name or type error for a missing one. Measured as a holder of Manage channels, in the
canary world:

    invalid name: hidden 400 "category not found"   | missing 400 "name is required"
    invalid type: hidden 400 "category not found"   | missing 400 the type error
    invalid sort order, a Stage on a text channel: the same answer for both

The fix's own claim (commit message, doc/api-stability.md bullet) is that a hidden category
answers like a missing one. This breaks it for a whole class of requests. Reach: Manage channels,
as in the original finding. Fix: check visibility where existence is checked. Pass the visibility
test into `CreateChannelWithStage` and apply it in `lockCategory` after the `SELECT ... FOR SHARE`
finds the row (answer `errNoCategory` there), or run `cleanChannelInputs` and `CheckSortOrder`
before the guard. The first option also fixes S1. Add the two invalid-input cases to the probe
test.

### S1 SHOULD-FIX: the hidden category answers faster than the missing one

The hidden path returns from an in-memory snapshot check (`internal/chat/core/guard.go:83-95`).
The missing path opens a transaction and runs the `SELECT ... FOR SHARE` first. Measured over
loopback, 300 alternating requests each, all answered 400 (none rate limited):

    channel in a category:  hidden p10/p50/p90 143/181/250 µs   missing 315/438/620 µs

The gap is about 250 µs at every percentile, larger than the spread, so a caller who repeats the
request can tell the two apart. Same reach as B1 (Manage channels). The B1 fix (checking inside
`lockCategory` after the row is found) gives both paths the same database work.

### S2 SHOULD-FIX: the api-stability bullet is under "3.0.0 changes"

`doc/api-stability.md:86-90` adds the bullet to the section that lists what the 3.0.0 major
release changed. This change ships in a 3.0.x patch, so the page now says that 3.0.0 made it.
The status change itself is acceptable. `api/openapi.json` documents 201, 400, 401, 403, 429 and
500 for `POST /api/admin/channels`, with no 404, so the old 404 broke the documented contract and
the new 400 conforms to it. Say that in the right place (the changelog, or a short "corrections
within 3.x" note) rather than in the 3.0.0 list.

### N1 NOTE: the same difference on a route outside the fix (layout)

`PUT /api/admin/layout`: moving a channel into a hidden category answers 404 "category not found"
(`internal/chat/channels/channel_permissions.go:116-117`), into a missing one 404 "channel or
category not found" (`channel_layout.go:118-119`). Ordering a hidden or a missing category answers
the same. Manage channels again. This is not part of H-L6-02's probes. It should be recorded as its
own finding, or folded into this fix; it is not a reason to hold this commit.

### N2 NOTE: `messages.ValidateReplyTarget` (no viewer) has no production caller

`internal/chat/messages/messages.go:245-247` is kept "for webhooks", but webhooks call only
`core.ValidateParent` (`internal/webhook/handler_store.go:39`). The function is used only by
`internal/chat/message_replies_integration_test.go`. Harmless; it could go, or its comment could
say it is for tests.

### B2 BLOCKER: the layout route still tells a hidden category from a missing one when a request has two faults

`CheckLayout` (`internal/chat/channels/channel_permissions.go:97-130`) now answers a hidden
category in each list on its own like a missing one. A missing category, though, is only noticed
later, in `ApplyLayoutTx` (`orderCategories`, then `placeChannels`). A hidden one is decided in
`CheckLayout` at a different point. So when a request has a second fault, the order of the checks
gives the hidden one away. Measured as a holder of Manage channels; the hidden and the missing
request differ only in the category id:

| Request | Hidden category | Missing category |
|---|---|---|
| D1: unknown category in the order list, target category hidden or missing | 404 "channel or category not found" | 404 "category not found" |
| D2: category in the order list hidden or missing, plus an unknown channel | 404 "category not found" | 404 "channel not found" |
| D3: as D2, with a channel hidden from the caller instead of an unknown one | 404 "category not found" | 404 "channel not found" |
| D4: target hidden or missing, then an unknown channel | same | same |
| D5: target hidden or missing, then a bad sort order | same | same |
| D6: category in the order list hidden or missing, plus a missing target | same | same |
| Single faults (unknown category in the list, unknown channel, hidden against unknown channel) | same | same |

Does a double fault tell more than a single request does? Yes. Single requests are now equal, so
D1 and D2 are exactly the bit the fix sets out to hide: whether a category id the caller cannot
see exists. Reach and gain are those of the original category variant (Manage channels, a known
category id, one bit), so this is S4. But the commit says "answers like a missing one at every
step", and this is a concrete case where it does not. The author already named double faults as
not done. My view: the gap is closed by the design, not by more special cases.

Fix (preferred): do not decide the hidden case in `CheckLayout`. Before `ApplyLayoutTx`, replace
every category id the caller cannot see, in both lists, with a fresh random id. Keep the
Administrator rule of `checkChannelMove`, treating the hidden target as unknown, as it does now.
Then the hidden request takes exactly the missing request's path: the same statements, the same
order of answers, the same database work. That also makes `errLayoutMissing` and the second
sort-order loop unnecessary. Add D1 and D2 as probes.

Alternative: take the layout part out of this commit, so the fix covers exactly H-L6-02's routes,
and record the layout difference as its own finding.

### S3 SHOULD-FIX (follow-up, not blocking): a rate limit can make an echo probe pass vacuously

`mustMatchMissing` counts any status of 400 or more as a refusal and compares the two answers. Once
a route's rate limit is reached, both sides answer the same 429 and the probe passes without
testing anything. My first generated run showed it: after about 600 layout requests from one
moderator, every further request answered 429, and my "0 differences" would have meant nothing
had I not counted the statuses. The author's generated test sends 600 layout requests in one world
and passes today with none rate limited, but it sits close to that point. One more probe for the
same user, or a lower limit, would silently empty it. Fix: in `mustMatchMissing` (and in the
generated test), fail on a 429 on either side.
