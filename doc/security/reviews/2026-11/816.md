## 1. Is the stated cause the real one?

### TestWSWriterPeriodicLifecycle/revoked and /deleted (internal/ws/hub_database_integration_test.go:157-165)

- The test's server-side connection has no read loop. The remote's pongs pile up unread, so when `writePump` closes the socket after the policy-violation close (lifecycle_pumps.go:81-86, :172-176), the kernel resets the connection.
- If the remote reads a ping that came before the close frame and answers it, the pong write fails with "broken pipe" (or reset). On main, the ping handler returned that error. gorilla's `advanceFrame` passes a handler error straight back, so `ReadMessage` returned it and never reached the close frame.
- Forced reproduction: I delayed the pong past the revocation (a 150 ms sleep in the handler after the third ping), 20 runs per variant.
  - With main's handler, the test failed with `write tcp ...: write: broken pipe, want policy violation`, which is the PR's error.
  - With the PR's handler it passed every time.
- Without forcing, main did not fail on macOS in 600 subtest runs (`-race -count=300`, revoked and deleted). The PR reports 3 in 600 on loaded Linux.
- Verdict: real cause. The fix is right: gorilla's default ping handler also treats the pong as best effort.

### TestTrickleAndAnswerShareTheSet (internal/sfu/candidate_dedupe_test.go:85-115)

- `vetAnswerCandidates` checks the answer's media sections against `PC.PendingLocalDescription()` (answer_candidates.go:35-39, :105-124). `Join` makes its offer on a goroutine of its own. When that offer was already pending, the old one-section `sdpHead` answer failed with `errAnswerSections`. When it was not yet pending, the check was skipped.
- main, `-race -count=200`: 1 failure, `vet: sfu: the answer's media sections are not the offer's`. That is exactly the stated cause.
- The PR waits for the offer, answers it with a real Pion client and appends the candidate line.
  - The answer carries no candidates of its own, because the client never calls SetLocalDescription and so never gathers. So `len(seen) == 1` still measures only the trickled candidate and the answer's copy of it.
- Product-wise there is nothing to hide here: a real client always answers the pending offer, and refusing a mismatched answer is the intended guard.

### TestPanicAfterTheMediaJoinRemovesThePeer (internal/ws/voice_seat_cleanup_test.go:124-153)

- On main, the test made the join panic by `close(first.send)`.
  - Production never closes `c.send` (no `close(c.send)` outside tests; `deliver` checks `closed` and never panics), so this was a test device only.
  - The tab's own SFU offer and candidates are sent from separate goroutines (attachPeer sendOffer/sendICE). If one of them hits the closed queue first, its recovery takes the tab out of voice, and the second join then has no sibling to tell. That matches the reported "the join did not panic".
- The new panic point is the existing `afterPeer` hook (voice_join.go:333-335), which runs right after `seatPeer`.
  - The old point was inside `evictSiblingConnections`. Both come after `c.setPeer(peer)` (voice_takeover.go:72), so the clean-up starts from the same state: the hub knows the peer and the SFU room holds it.
  - The new assertion `c.peer() != nil` pins that, so the hook cannot move before the attach unnoticed.
- I did not reproduce main's failure (the PR also could not reproduce it). The mechanism follows from the code, and the new form has no goroutine left in the decision.

## Notes (none blocking)

1. **Lifecycle: the reset is the root, and the PR now tolerates it.** The pong fails because the test's server conn is never read, so the close turns into a reset. In production `readPump` drains the socket, so there is no product race. In principle a reset could also make the remote's read fail before it takes the close frame from the kernel buffer. I did not see that in 400 revoked/deleted runs on the PR, and the PR's 1000 runs did not show it either. If it ever shows up, a drain goroutine on `server` in the test (as a real read loop would be) removes the reset itself.
2. **`mnema_noise=off` is now written at every page load of every context**, in non-call specs too (helpers.ts:103). helpers.ts says a spec that checks the filter turns it back on with its own init script. That covers checking the default, but not a future spec that picks a filter in the settings dialog and reloads to see that it persisted: the init script resets it on each load. Today no spec touches the noise setting (grep for `noise`, the German labels and the setting's test ids in `e2e/tests`). One sentence in the comment would prevent the surprise.
3. **The AI filter now runs in fewer specs.** Contexts that had no recorder on main ran DeepFilterNet3 by accident: stage-switch member B, hidden-video, screen-layers. They no longer do. The filter path itself stays covered, CSP included through the auto fixture, by late-join (which checks the `deepfilter-worker-bridge`), perf-idle and audio-stall. This is intended, but worth knowing.
4. **The panic test no longer goes through a sibling tab.** It now proves clean-up after a panic at the hook, not at "telling the other tab". Both points come after `setPeer`, so for the clean-up they are the same. The eviction path itself is covered by the takeover tests.
5. The recorder wraps `RTCPeerConnection` in every frame of every context, also in specs that never call. This is harmless (a subclass, no behaviour change), and the new `try` around `localStorage` covers frames without storage.
