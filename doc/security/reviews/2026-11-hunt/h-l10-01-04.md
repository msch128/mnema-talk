## H-L10-01: retry ids and upload bookings of an erased account (fix-h-l10-01)

**Cause removed: yes.** `chatEraseSteps` (internal/chat/account/account_erase.go:58-62) gains `DELETE FROM message_nonces WHERE user_id = $1` and `DELETE FROM upload_usage WHERE user_id = $1`. They run in the erasure transaction with new order numbers (internal/userdata/order.go:75-76), after the login-unlock step. Both tables are covered by an index on `user_id`: the primary key of message_nonces (user_id, nonce) and `upload_usage_user_idx`. So each step is an index scan over one member's rows, which is cheap. Every writer of upload_usage is covered by the one statement: attachment upload, staged upload, wiki images, and webhook files (the webhook files writer books a bot account). The order test (`TestAccountErasureKeepsTheOriginalStatementOrder`) lists both statements.

**Lock order and deadlocks.** The erasure starts with `SELECT ... FROM users WHERE id = $1 ... FOR UPDATE` (internal/auth/account/account_erase.go:82). Every insert into either table checks its foreign key, which takes FOR KEY SHARE on the same users row. FOR KEY SHARE conflicts with FOR UPDATE. So a send or upload either holds that lock before the erasure starts, and the erasure waits for it at its first statement and then deletes the committed rows, or it waits for the erasure. The send transaction writes its nonce after the message insert (internal/chat/messages/post.go:121-127), and an upload writes its usage row after the media insert (internal/media/handler_upload.go:131-138, staging.go:108-114). Both inserts take the users lock first, so a send or upload holds no lock on a nonce or usage row of this person before it competes for the users row. The other writers that lock existing rows are the two pruners and the ON DELETE SET NULL of message_nonces.message_id. The pruners lock only the rows they delete and never need the users row. The cascade fires only on deletion of the person's own messages, which the erasure has already locked at its earlier messages step. I found no lock cycle that involves the two new statements. A deadlock that involves earlier steps would exist without this fix, and PostgreSQL resolves one by aborting a transaction (the erasure answers 500 and can be retried).

**Remaining leak in flight (NOTE, existed before this fix, much wider than these two tables).** A request authenticated before the erasure commits, whose insert waits on the users row or arrives after the commit, still writes its rows after the erasure. Nothing in the send transaction checks `deleted_at`. The tombstone trigger `users_deleted_final` (migration 0043) allows the `message_count` counter update once `disabled_at` is set. A SQL-level model of a send in flight, run against the test database, showed this:

- the erasure's FOR UPDATE was held;
- a concurrent `INSERT INTO messages ...` plus `INSERT INTO message_nonces` was blocked;
- then the erasure deleted nonces, emptied messages, set `deleted_at` and `disabled_at`, and committed;
- the blocked insert then went through;
- result: `nonces=1 messages with text=1`.

So the nonce row lasts until the pruner runs, up to about 25 hours, as before the fix. A whole message with its text, and a reaction, upload or any other plan table written the same way, lasts permanently. The window is one request's latency at the moment the person erases their own account, for example while sending from a second tab. The cause is that the send and upload paths do not re-check the author inside their transaction. That is outside H-L10-01 and this fix. I report it to the coordinator as a candidate for a new finding (likely S4) and do not hold the fix for it.

**The guard (`requireEraseStatementsForEmptyTables`, internal/server/account_delete_integration_test.go:71-90).** It now fails for a foreign key to users that the fixture leaves empty, unless an erasure statement names the column or `erasureKeeps` gives a reason. Probes I added in a scratch test, each run alone:

- New table `probe_notes(author_id uuid REFERENCES users(id))`: **fails** with "probe_notes.author_id: the fixture has no row and no erasure statement names it". Correct.
- Second column on a table the plan already deletes from (`ALTER TABLE message_nonces ADD COLUMN reviewer_id uuid REFERENCES users(id)`): **passes**. `erases()` (internal/server/personal_schema_integration_test.go:119-129) accepts any `DELETE FROM <table>` regardless of the WHERE column, but `DELETE ... WHERE user_id = $1` leaves rows where only reviewer_id names the person.
- Column named like a JSON key in an UPDATE of the same table (`ALTER TABLE message_reports ADD COLUMN user_id uuid REFERENCES users(id)`): **passes**. The snapshot scrub statement contains `'user_id'` inside a JSON path, so the word-boundary match succeeds.
- Real schema: with a stricter matcher (the column must appear as `col =` or `col IN` in a DELETE/UPDATE of the table), no current column changes verdict. The only columns not matched are the bot columns that `erasureKeeps` lists.

So the guard still passes vacuously for a forgotten second column on a table that is already erased, in a fixture that leaves it empty. Today no real column falls in that gap.

Findings for this fix:

- **SHOULD-FIX (non-blocking):** tighten `erases()` so the column must appear in the WHERE clause (for DELETE) or in SET/WHERE (for UPDATE). With that change the real schema still passes, and both coincidence probes fail. Until then, SECURITY.md:418-419 ("fails when a table that refers to a person is forgotten") is true for tables, not for columns.
- **NOTE:** upload_usage is a media table, but it is deleted from the chat erase steps. It works because the order is global. A media-side registrar would be tidier.

## H-L10-03 and H-L10-04: orphan cleanup of exports/, guide prefixes (fix-h-l10-03)

**Cause removed: yes.**

- `orphanPrefixes` (internal/media/orphans.go:26) gains `exports/`.
- `orphanLookup` (:73-78) checks `exports/` keys against `data_exports.s3_key` and the four media spaces against media rows as before.
- `sc.lookup` is set per prefix, and the batch is flushed at the end of every prefix (:64-66). So a partial batch of one prefix is never checked with another prefix's query.

This covers every variant in the finding and the refuter's report:

- a failed DeleteBatch after the erasure;
- a crash between the erasure commit and the delete;
- the build that finishes after the erasure deleted its row (account_export_build.go:131-137, whose error is dropped);
- a failed delete after a failed build.

**Can it delete an export that is still wanted? No, as long as the row exists.** Write order in `buildExport` (account_export_build.go:103-138): the object is uploaded first, then `UPDATE data_exports SET status='ready', s3_key=...`. The build runs under `exportBuildTimeout` = 5 minutes (account_export.go:25, :128). So an object without its row is at most 5 minutes old, well inside the 24-hour age rule (`orphanMinAge`).

Object age comes from the store's `LastModified` in ListObjectsV2 (internal/s3/s3.go:230), compared against the app's clock. The export upload is a multipart upload (internal/s3/stream.go:75). Stores differ on whether LastModified is the initiation or the completion time. I did not check this against SeaweedFS or other stores. With either meaning, it lies at most one build (5 minutes) before the row is written, so the rule holds. An incomplete multipart upload is not listed and so not touched. Clock skew between app and store would have to be close to 24 hours to matter.

Once written, the row keeps the key until the object is gone:

- `dropExportFile` deletes the object first and clears the key only on success (account_export.go:288-296);
- the sweep goes through `dropExportFile`;
- rows are pruned only when `s3_key IS NULL` (:347).

Probe of my own (API level, objects 48 hours old):

- **Kept** (a row names each one):
  - a downloaded export whose delete had failed (row keeps the key);
  - an expired export the sweep has not reached;
  - a failed row that still holds a key.
- **Deleted** (`Count:2 Deleted:2`):
  - an object of a pending row without a key;
  - a stray `exports/not-an-export.txt`.
- **Dry run:** `GET /api/admin/media/orphans` first returned `Count:2 Deleted:0` and removed nothing.
- **Access:** a member got 403 on both routes. Both are Owner-only (internal/media/handler.go:121, `auth.RequireOwner`). The cleanup answers 409 during an online backup (`TryOutsideBackup`). Nothing deletes on its own: the daily job only counts.

The author's own test covers another member's live export with its row (kept), a young archive without a row (kept), and the left-over upload and export (both deleted). The author also reports that a version checking exports/ against media rows deletes the live export. I did not rerun that variant; the lookup switch is exactly what prevents it.

**Restored backup with a database older than the object store.** Exports built after the database snapshot have no rows after a restore. Once their objects are 24 hours old, the Owner's cleanup deletes them. That is acceptable for three reasons:

- such an export cannot be downloaded, because `claimDownload` needs the row (account_export.go:261-270);
- after 24 hours it would have expired anyway;
- uploads/ objects in the same situation have no media rows and have always been deleted the same way.

The online backup freezes storage before the database snapshot, so there the only case is an export whose upload finished just before the freeze while its UPDATE came after. That export is pending in the restored database, the sweep marks it failed, and its object becomes an orphan. Correct. The orphan section of doc/operations.md describes the rule generally ("no data export row") but says nothing about restores. That is acceptable: the uploads/ case was not documented either. NOTE.

**Behaviour change for shared buckets (NOTE).** Objects of other software under `exports/` in the same bucket were never touched before. They are now deleted once 24 hours old when the Owner runs the cleanup. The guide states the new rule ("anything outside those five prefixes are never touched"), and `exports/` was already the app's own key space, where any foreign object could collide with the app's writes. No upgrade note exists. The commit subject will appear in the changelog. I consider that enough for a patch release.

**Documentation.**

- doc/operations.md "Orphaned media" now names all five prefixes and what refers to each, which fixes H-L10-04 ("two" after three names, without `covers/`). The guide test is a plain assertion now.
- The SECURITY.md parenthesis ("the orphan cleanup removes only an archive no export row names") is true; the 24-hour rule applies on top.
- The account-deletion paragraph of doc/operations.md:1658-1660 and the `removeObjects` comment are true now.

**SHOULD-FIX: swagger description.** The `@Description` of GET /api/admin/media/orphans (internal/media/handler_admin.go:152) says "Objects in storage (uploads/, avatars/) that no media row refers to". It was already stale (banners/, covers/ missing) and now also omits exports/, whose reference is not a media row. The cleanup description (:177), "Never touches an object a media row refers to", is incomplete for exports/. The published API reference (api/openapi.json) therefore tells an Owner less than the guide does. The fix: update both descriptions and run `make openapi`. A description change is not breaking for openapi-diff. Not blocking on its own. `make openapi-check` passes on the branch as it is (exit 0, no diff), because the generated file matches the unchanged annotations.

**NOTE:** `exportKeys` (`WHERE s3_key = ANY($1)`) has no index on data_exports.s3_key. The table holds at most a few rows per member (rows are pruned after 7 days), and the cleanup is a manual Owner action. No cost on a hot path.
