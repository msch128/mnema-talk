## SHOULD-FIX

### S1. Parallel downloads all win the "single-download" claim (exists on main too)

`internal/auth/account/account_export_download.go:97-104` (`claimDownload`).

- The claim is `UPDATE … WHERE id = (SELECT id … AND (claimed_at IS NULL OR
  claimed_at < NOW() - 10 min) … LIMIT 1)`. Under READ COMMITTED the subquery
  is evaluated once, with the statement's snapshot. A second caller that waited
  on the row lock re-checks only `id = <that id>` against the new row version,
  not the claim condition, so it also succeeds. This is the codebase's own
  lesson: no condition in a subquery under a row lock.
- Evidence (scratch integration test, six goroutines released together,
  `claimed_at` reset between rounds): on the branch, 29 of 30 rounds let all six
  callers claim (`round 1: 6 callers claimed the export at once` … `29 of 30
  rounds let more than one download hold the claim`). The same probe against
  `origin/main` (its three-value `claimDownload`): 30 of 30 rounds.
- Consequence: SECURITY.md ("only one download holds it at a time") and the
  PR description ("the 10-minute single-download claim" unchanged) are not
  true. With the hour, extra copies within the hour are allowed anyway, so the
  harm is small: parallel transfers of one archive, each audited. Even so, the
  documented invariant of a protected area is false.
- Smallest fix I accept (verified: the probe then passes in all 30 rounds, and
  the existing and new export tests stay green): keep the subquery only to pick
  the newest ready row, and put every condition in the outer `WHERE`, which
  PostgreSQL re-checks on the locked row:

  ```sql
  UPDATE data_exports SET claimed_at = NOW()
  WHERE id = (SELECT id FROM data_exports WHERE user_id = $1 AND status = 'ready'
              ORDER BY requested_at DESC LIMIT 1)
    AND status = 'ready' AND s3_key IS NOT NULL AND expires_at > NOW()
    AND (downloaded_at IS NULL OR downloaded_at > NOW() - $2 * INTERVAL '1 second')
    AND (claimed_at IS NULL OR claimed_at < NOW() - INTERVAL '10 minutes')
  RETURNING id, s3_key, size_bytes
  ```

  The repo's other pattern is just as good: lock the newest row
  `FOR UPDATE` in a transaction, then claim it in a new statement. Add the
  parallel test (racetest style) so this stays fixed.

### S2. A response shorter than its Content-Length counts as a complete download

`internal/auth/account/account_export_download.go:70-79`.

- Content-Length comes from `size_bytes` and the body comes from the store.
  `size_bytes` is `counted.n`, the bytes the archive writer passed into the
  upload pipe (`account_export_build.go:111,133-135`), so the two agree as long
  as the store returns what it took. I found no code path that makes them
  differ. They differ only if the stored object is truncated or replaced.
- What each side then sees (scratch test over a real `httptest.Server`):
  - Object 100 bytes longer than `size_bytes`: the first `Write` exceeds the
    declared length and Go writes nothing (`http.ErrContentLength`). The
    handler releases the claim and the client gets `unexpected EOF`. The export
    is not counted. This is safe.
  - Object 100 bytes shorter: `io.Copy` returns no error, so the server records
    `downloaded_at`, writes `auth.export_download` and starts the hour. The
    client reads 5356 of 5456 bytes and gets `unexpected EOF`. Every retry in
    the hour fails the same way. Before this change there was no
    Content-Length, so a client always got the whole object.
- Smallest fix: compare the count. `n, err := io.Copy(w, body); if err == nil &&
  n != size { err = io.ErrUnexpectedEOF }` treats the transfer as interrupted.
  The current branch logs that, releases the claim and records nothing.
- Range, compression, HTTP/2: no compression middleware sits on the API routes
  (none in `internal/server`, `internal/httpx`), so nothing rewrites the length.
  `Range` is ignored: the answer is always the whole file with 200, which is
  correct with Content-Length. On HTTP/2, Go enforces the declared length the
  same way as on HTTP/1.1.

### S3. The sweep removes the file under a running download, and the archive's own README is now wrong

- `internal/auth/account/account_export.go:272-273`: the sweep's new branch
  (`downloaded_at < NOW() - 1 h`) ignores `claimed_at`. Probe: complete
  download; `downloaded_at` moved to 59 minutes ago; a second download claims;
  the hour ends; the sweep runs. Result `{downloaded:true claimed:true
  hasKey:false} files=0`. With the S3 client an already-open GET usually keeps
  streaming after a DELETE, but that depends on the store, and I did not check
  it on SeaweedFS or MinIO. The same edge existed at the 24-hour expiry. The
  hour makes it common: any second download started in the hour's last minutes
  of a slow link. Smallest fix: `AND (claimed_at IS NULL OR claimed_at < NOW()
  - INTERVAL '10 minutes')` on the sweep's selection. A claim is at most ten
  minutes, so the file goes at the next sweep after the claim ends.
- `internal/auth/account/account_export_build.go:98`: the README inside every
  archive still says "This file was available for download once, for 24
  hours." That is the member's own record of the retention, and it is now false.
  Change it to the new rule (for example "This file could be downloaded for 24
  hours; it was removed one hour after the first complete download.").

## NOTE

- **Audit outside the transaction (unchanged from main).** `finishDownload`
  (`account_export_download.go:116-119`) and `AuditUser`
  (`account_export_download.go:79`) are two separate statements, and errors are
  ignored. Every complete download is audited, including repeats in the hour,
  but not atomically with `downloaded_at`. The codebase's rule is audit inside
  the transaction: one `pgx.BeginFunc` with the `UPDATE` and
  `h.Audit.RecordTx` (as `eraseInTransaction` does) closes it. Not required for
  this change.
- **`finishDownload` clears any claim.** `claimed_at = NULL` is unconditional,
  so a download that ran past its ten-minute claim clears a newer claim. After
  S1 it matters little; `AND claimed_at = <own claim time>` would make it exact.
- **Stolen session.** SECURITY.md says the hour "gives a stolen session no file
  it could not already take in the 24 hours before the member's own download".
  That holds for a session stolen before the download. A session stolen after
  it gains one hour it did not have before. The archive's content is what the
  same session can mostly read through the API anyway, and every download is
  audited, so I accept the trade-off. Suggested wording: "The hour gives a
  stolen session at most one more hour to take the same file; …".
- **Retention wording.** `doc/operations.md:1684-1685` says "one hour after the
  first complete download, at the latest". The sweep runs every 15 minutes and
  waits for an online backup, so the file can stay up to about 1 h 15 min. The
  "at most 24 hours" before it has the same slack. "Removed by the next sweep
  (every 15 minutes) after that hour" is exact.
- **German intro text.** `web/src/i18n/de.json` `exportIntro`: "du kannst ihn
  24 Stunden lang herunterladen". "ihn" has no masculine antecedent in that
  paragraph (it starts with "Eine ZIP-Datei"). Use "sie" or "den Export".
- **The web UI does not use `downloaded_at`.** After a download the button
  again reads "Download (valid until HH:MM)" with the end of the hour. That is
  correct, but it does not say the file was downloaded already. Optional.
- **Test hygiene.** `TestATransferCutInTheMiddleKeepsTheExport`
  (`account_export_download_integration_test.go:126-147`): when the status or
  length check fails, `t.Fatalf` runs before `resp.Body.Close()`. The deferred
  `srv.Close()` then waits for a handler blocked writing 32 MiB to a reader
  that never reads, and the package hangs until the 10-minute test timeout (seen
  with the behaviour reverted). Add `defer resp.Body.Close()` right after
  `http.Get`.
- **Swag order.** In `account_export_download.go` the `@Header 200
  Content-Length` line sits between the `@Failure` lines. That is harmless (the
  generated document is right) but easy to misread.
- **Older edge, unchanged.** `expires_at` is `ready_at + 24 h` and the daily
  limit runs from `requested_at`. For the length of one build (at most five
  minutes) a new export can be requested while the old one is still
  downloadable. The hour does not widen this: a downloaded export's window ends
  at the earlier of the two.

### The claim token

- **Precision.** `claimed_at` is `TIMESTAMPTZ` (`0043_account_privacy.sql:25`),
  stored in microseconds. pgx moves it in the binary format as an int64 of
  microseconds in both directions, and no JSON is on the path: the token lives
  only inside the request. A probe ran 300 rounds of claim and release with the
  token from `RETURNING`, then a finish. Every release freed the claim, the
  finish recorded the download and freed the claim, and no token had a
  sub-microsecond part. The time zone of the scanned `time.Time` does not
  matter: the value compares as an instant.
- **`clock_timestamp()` against `NOW()`.** The claim stores
  `clock_timestamp()`, which is a little later than the statement's `NOW()`, and
  the lapse compares with `NOW()` of later statements. Only the database clock
  is involved; the app clock is not. A clock stepped back makes a fresh claim
  last longer than ten minutes: the member gets 404 until the clock catches up,
  and nothing leaks. A clock stepped forward lets a claim lapse early, so a
  second download can claim while the first still runs. The tokens differ, so
  neither ends the other's hold, and both transfers are whole copies of the same
  file, each audited.
- **The 10-minute edge.** The server's `WriteTimeout` is 10 minutes
  (`internal/server/run.go:27`). It starts before the handler claims, so a
  transfer is cut by the server before or at the moment its claim lapses. A
  second holder at the edge therefore overlaps a dying transfer by at most
  milliseconds. When the cut transfer releases, its token no longer matches and
  it leaves the new claim alone.
- **The sweep and a new claim at the same time.** They cannot both act on one
  row. The sweep only selects rows past their hour or their expiry. A new claim
  needs a row inside the hour and before its expiry. The two sets do not
  overlap at any instant. The one remaining gap is the sweep's select, then its
  object delete, then `s3_key = NULL`, without re-checking the claim. A claim
  cannot start on such a row in between, because the row is already past its
  hour.

### Notes (round 2)

- **N1. No test pins the audit to the transaction.** Reverting to the old
  `AuditUser` after the commit keeps every test green. A test that makes the
  audit insert fail (for example a `CHECK` added to `audit_log` in the test)
  and expects `downloaded_at` to stay NULL would pin it. Optional.
- **N2. A failed audit insert leaves the claim held.** The rollback also
  undoes `claimed_at = NULL`, so the member gets 404 for up to ten minutes
  after a complete copy, and nothing is recorded. The rollback is the right
  outcome for "audit in the transaction". A `releaseDownload(c)` after a
  failed transaction would end the wait early. Optional.
